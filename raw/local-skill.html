PAGE 1 · 1-Execution Architecture and Payload Lifecycle.md

Execution Architecture and Payload Lifecycle

Ghost is organized as a compact loader pipeline whose main function coordinates preparation, decoding, memory placement, and repeated execution. Before touching the embedded payload, startup restores the local ntdll code and disables selected ETW paths. It then retrieves the RCDATA resource, copies its ciphertext into owned memory, and passes the bytes through the BCrypt-backed AES-CBC routine. The decrypted buffer is not executed in place. Instead, the allocator reserves a region far larger than the payload, fills it with random bytes, chooses an offset, and copies the plaintext into that concealed location.

Payload Preparation

The resource, cryptography, and allocation helpers form a staged transformation. Resource APIs expose an opaque byte range and its size; AES decryption produces a separate plaintext allocation; randomized placement moves those bytes into the final large region. Temporary ciphertext and plaintext allocations are released after transfer, while the large-page metadata remains live because it owns both the allocation base and the selected entry address. The main routine changes the region from writable to executable-read only after placement, keeping the write and execute phases separate.

flowchart TD A[Embedded RCDATA] --> B[Copy ciphertext] B --> C[AES-CBC decrypt] C --> D[Allocate oversized region] D --> E[Fill with random bytes] E --> F[Copy payload at random offset] F --> G[Protect as executable-read]

Fiber Execution Loop

Execution uses two fibers on one thread. The original thread becomes the initial fiber, while a second fiber starts at the concealed payload address. Sleep is redirected to a switcher that records the requested delay and returns control to the initial fiber. The initial fiber performs the actual native wait and then re-enters the payload fiber. This division means the payload stack is suspended rather than remaining active during the sleep interval.

flowchart TD I[Initial fiber] --> P[Payload fiber] P --> S[Hooked Sleep] S --> I I --> W[Native event wait] W --> P

Ownership and Failure Boundaries

The lifecycle relies on shared globals for the spoofing gadget, fiber handles, delay duration, decrypted output, and large-page context. Initialization order is therefore part of the design: the gadget and resolver-backed function pointers must be usable before helper calls, the payload address must be valid before fiber creation, and the current thread must be converted before switching. Error checks around decryption, allocation, protection, and resource lookup define the main failure boundaries. Understanding these transitions is the basis for safely changing payload handling without breaking the execution scheduler.

PAGE 2 · 1.1-Startup Orchestration.md

Startup Orchestration

Initialization Order

Ghost's main function is a strict coordinator rather than a general service loop. It first restores ntdll and patches ETW, then retrieves and decrypts the embedded payload, prepares its memory, installs the Sleep hook, and creates the fibers. The ordering matters because later helpers depend on the resolved function table and spoofing gadget initialized at process start.

Shared Runtime State

Several globals connect otherwise separate headers: the gadget address is passed to RetSpoofCall, the large-page context keeps both allocation base and payload entry address, and fiber handles plus the requested delay coordinate switching. These values make the program compact, but they also mean initialization cannot be safely reordered without tracing dependencies across files.

Failure Boundaries

The main path exits on failed decryption and uses native-status validation around memory protection. Resource and setup helpers often print diagnostics but do not always stop immediately, so callers must understand which outputs may remain invalid. Cleanup releases temporary ciphertext and plaintext buffers after the final copy while retaining the executable allocation.

Control Flow

flowchart TD A[Restore ntdll] --> B[Patch ETW] B --> C[Load and decrypt resource] C --> D[Place payload] D --> E[Install hook and fibers] E --> F[Execution loop]

This orchestration page is the best starting point when changing startup behavior because it exposes the complete dependency order and the handoff between subsystems.

PAGE 3 · 1.2-Resource Decryption Pipeline.md

Resource Decryption Pipeline

Embedded Input

The build embeds encrypted bytes as an RCDATA resource with identifier 101. At runtime GetFromRc uses resolved resource APIs through RetSpoofCall to locate, load, lock, and size that data. The returned pointer belongs to the module resource, so Ghost.cpp copies it into a separately allocated ciphertext buffer before decryption.

AES-CBC Processing

AESDecrypt opens the BCrypt AES provider, configures CBC chaining, creates a symmetric key from the generated key bytes, queries the required plaintext size, allocates output storage, and decrypts with block padding. The IV is supplied from the arrays compiled into Ghost.cpp, matching the values produced by the build script.

Ownership Transfer

flowchart LR R[RCDATA bytes] --> C[Owned ciphertext] C --> A[AESDecrypt] A --> P[Plaintext buffer] P --> M[Randomized executable region]

After the plaintext is copied into the large allocation, the temporary ciphertext is freed and the plaintext array is deleted. The large allocation remains because its random interior address becomes the fiber entry point.

Maintenance Notes

The resource file, generated key arrays, and decryptor form one contract. Replacing only icon.ico or only the source arrays produces an undecryptable executable. Error handling should also be reviewed carefully if this pipeline is hardened, because resource lookup failures currently report diagnostics but may allow subsequent operations to continue.

PAGE 4 · 1.3-Randomized Payload Memory.md

Randomized Payload Memory

Allocation Strategy

allocate_large_page expands the requested payload size by a factor of 2048 and page-aligns the result. It reserves and commits the region as read-write memory through NtAllocateVirtualMemory, then fills the entire allocation with bytes from SystemFunction036. This creates a large noisy region instead of a compact buffer whose boundaries directly reveal the payload.

Offset Selection

The allocator chooses a pseudo-random offset and records both the allocation base and lpData, the intended payload address. place_data_rand copies the decrypted bytes to that address through the common spoofed-call wrapper. The context is later used for protection changes and fiber creation, so both addresses have distinct roles.

Protection Transition

flowchart TD A[Payload size] --> B[Multiply and align] B --> C[Reserve read-write region] C --> D[Fill random bytes] D --> E[Choose offset] E --> F[Copy plaintext] F --> G[Protect executable-read]

Ghost.cpp changes protection on the complete allocation only after the payload is placed. The payload entry passed to CreateFiber is the interior lpData pointer, while protection APIs receive the allocation base and total size.

Safety Considerations

The random offset calculation is central to correctness: the chosen position must still leave enough space for the payload. Any allocator change should preserve page alignment, validate allocation and random-fill results, and ensure the copy cannot exceed the reserved region. The current design prioritizes concealment and assumes those invariants hold.

PAGE 6 · 2-Dynamic Resolution and Call Concealment.md

Dynamic Resolution and Call Concealment

Ghost replaces much of the ordinary Windows import-and-call path with a runtime binding layer. Module discovery starts from the process environment block, while export resolution parses PE structures already mapped in the process. Names are compared through custom hashes, allowing the program to initialize a table of function pointers without exposing every target through conventional imports. The same resolver family inspects ntdll syscall stubs so native operations can be invoked with runtime-derived service numbers and syscall instruction addresses.

Runtime Binding

The resolver layer separates three concerns: finding a loaded module, finding an export inside that module, and deriving syscall metadata from neighboring stubs when a target appears hooked. Shared declarations in the type and structure headers reproduce the Windows data layouts and signatures required by those operations. functions.h then assembles the results into global pointers used by memory management, process creation, resource access, cryptography, event waiting, and fiber APIs.

flowchart TD P[PEB loader lists] --> M[Hashed module match] M --> E[PE export directory] E --> F[Resolved function pointer] E --> N[Inspect ntdll syscall stubs] N --> S[SSN and syscall address]

Return-Address Spoofing

RetSpoofCall is a variadic bridge between C++ callers and arbitrary target functions. The C++ helper locates call-through-R12 gadgets in executable ntdll sections. The assembly routine saves nonvolatile state, rearranges arguments into the Windows x64 register and stack convention, substitutes the selected gadget as the apparent return site, and transfers control to the requested function. When the target returns through the gadget, a fixup restores the original frame and registers. This primitive is reused broadly, so its argument-count contract and stack layout are central architectural constraints.

sequenceDiagram participant C as C++ caller participant R as RetSpoofCall participant T as Target API participant G as ntdll gadget C->>R: target, count, gadget, arguments R->>T: rearranged native call T->>G: apparent return G->>R: jump to fixup R-->>C: restore frame and return

Indirect Native Calls

The syscall assembly stubs preserve ordinary native signatures while loading a discovered service number and jumping to a discovered syscall instruction. Higher-level code therefore does not hard-code version-specific numbers. The design composes dynamic resolution, hook inspection, indirect syscall dispatch, and return-address spoofing rather than treating them as isolated tricks. A change to a native signature or resolver result can propagate into global declarations, call counts, register placement, and assembly behavior, so these layers must be reviewed together.

PAGE 11 · 3-Telemetry Suppression and Sleep Evasion.md

Telemetry Suppression and Sleep Evasion

Ghost prepares its process environment before launching the payload and changes behavior again whenever the payload sleeps. The preparation sequence first replaces the local ntdll text with bytes read from a clean image in a suspended helper process, then patches selected ETW entry points. During execution, an inline hook redirects Sleep to a fiber switcher. These mechanisms share native memory-protection operations and the return-spoofed call layer, but they address different observation surfaces: user-mode hooks, event tracing, and a visible sleeping payload stack.

Restoring ntdll

The unhooking routine creates audiodg.exe in a suspended state through a native process-creation path. It determines the local ntdll image size, reads the corresponding remote image into a buffer, locates the text section through PE headers, temporarily changes the local section protection, and copies clean bytes over the current text. The helper process is terminated after the read. This sequence depends on indirect syscall stubs for process creation, remote memory reads, protection changes, and termination, reducing reliance on the potentially instrumented functions being repaired.

flowchart TD A[Create suspended audiodg] --> B[Read clean ntdll image] B --> C[Locate local and remote text sections] C --> D[Make local text writable] D --> E[Copy clean section] E --> F[Restore protection] F --> G[Terminate helper]

ETW Patching

The ETW routine resolves NtTraceEvent and NtTraceControl by hash and modifies each function in memory. It protects the relevant region for writing, places a return opcode at the chosen offset, verifies the patch, and restores the prior protection. This is intentionally narrow compared with whole-section restoration: unhooking replaces a section from a clean process, whereas ETW suppression applies targeted modifications after that restoration. Their ordering in main is therefore meaningful.

Sleep and Fiber Handoff

HookFunction installs an absolute jump at the selected sleep API. When the payload requests a delay, FiberSwitcher records the duration and switches back to the initial fiber. The main loop then waits through NtCreateEvent and NtWaitForSingleObject before re-entering the payload fiber. The payload's execution stack remains suspended while the initial fiber owns the wait, which is the core sleep-evasion behavior.

sequenceDiagram participant P as Payload fiber participant H as Sleep hook participant I as Initial fiber participant N as Native wait APIs P->>H: Sleep milliseconds H->>I: switch and record delay I->>N: create event and wait N-->>I: timeout completes I->>P: resume payload fiber

The implementation assumes that the chosen payload actually sleeps through the hooked API. Adapting another payload family may require identifying a different blocking function and redirecting that function to the same scheduling concept.

PAGE 13 · 3.2-ETW Function Suppression.md

ETW Function Suppression

The loader suppresses selected Event Tracing for Windows paths during startup by modifying two native routines already mapped from ntdll.dll. The implementation is concentrated in PatchETW() and runs immediately after the clean-image restoration step, before the encrypted resource is loaded or decrypted. This ordering matters: the program first replaces the local ntdll text with bytes read from a suspended helper process, then applies its own targeted modifications to that restored image.

Startup Position

main() invokes FlushNTDLL() and then PatchETW(). Only after those preparation stages does it read the RCDATA payload, allocate a ciphertext buffer, decrypt it, and place the plaintext in randomized memory. ETW suppression is therefore part of process preparation rather than part of the later fiber scheduling loop.

graph TD Start([Process start]) --> Restore[Restore local ntdll] Restore --> Patch[Patch ETW routines] Patch --> Resource[Read encrypted resource] Resource --> Decrypt[Decrypt payload] Decrypt --> Execute[Prepare payload execution]

The function returns void, so callers receive no explicit success value. Failures are handled inside the patch routine through validation macros or diagnostic messages, and main() continues after the call returns. This means the loader treats ETW suppression as a preparatory best-effort step rather than a result that gates decryption.

Resolving the Targets

PatchETW() does not import the target functions by name. It first obtains the loaded ntdll module through GetLoadedDllHandleH() using a fixed hash. That resolver walks the process environment block loader list and hashes module names. It then calls GetFunctionAddressH() with separate hashes for NtTraceEvent and NtTraceControl. The export resolver parses the module's PE headers, export-name array, ordinal array, and function-address array until the requested hash matches.

The returned addresses are converted to byte pointers. The code does not patch the first byte of either export. Instead, it adds an offset of three bytes to each resolved address and stores those adjusted locations in EventProtectionOffset and ControlProtectionOffset. A single byte containing 0xC3, the x64 return opcode, is prepared as the replacement. Consequently, the intended effect is an early return inside each native tracing entry point after its initial bytes.

Writable Protection Transition

Executable image sections are not normally writable, so the routine changes protection around each one-byte target. It uses the globally resolved NtProtectVirtualMemory pointer from functions.h, but invokes it through RetSpoofCall. The arguments identify the current process through SELF_HANDLE, pass the address by reference, pass a one-byte region size, request PAGE_EXECUTE_READWRITE, and receive the previous protection value. Separate old-protection variables are retained for the control and event targets.

graph TD Resolve([Resolved export]) --> Offset[Advance three bytes] Offset --> Writable[Set executable writable] Writable --> Copy[Copy return opcode] Copy --> Verify{Byte matches} Verify -->|No| Abort[Print error and return] Verify -->|Yes| Restore[Restore prior protection] Restore --> Complete[Patch complete]

The protection calls are checked with NTAPI_VALIDATE_RETURN2VOID. Although the macro definitions live with the shared native interface, their role here is to stop this function when a native operation does not return an acceptable status. The two targets are handled independently: protection is changed for NtTraceControl first and for NtTraceEvent second.

Patch and Verification

The actual write uses the return-spoofing bridge to call memcpy for one byte. NtTraceControl is patched first. ValidateMemory() then calls memcmp, also through RetSpoofCall, to compare the destination with the prepared source byte. A nonzero comparison prints a specific data-mismatch message and returns. The same copy-and-compare sequence is then applied to NtTraceEvent.

Only after both comparisons succeed does the function restore the original memory protection for each adjusted address. Restoration again uses NtProtectVirtualMemory through RetSpoofCall, passing the saved protection values. Under _DEBUG_PRINT, successful completion emits a short confirmation.

This sequence has an important failure boundary. If verification of either copied byte fails, the function returns before the final protection-restoration calls. A failure after the first protection change can therefore leave one or both one-byte regions writable. Similarly, the routine does not explicitly flush the instruction cache after modifying executable code. The source relies on the immediate byte write and subsequent execution behavior rather than calling a cache-flush API.

Shared Native Interface

functions.h initializes NtProtectVirtualMemory by resolving its hashed export from the loaded ntdll handle. The same header also discovers a system-call number and a syscall instruction address for that API, but PatchETW() uses the resolved function pointer with the return-spoofing bridge rather than the indirect syscall assembly stub. This distinction separates two concealment mechanisms: hashed resolution removes ordinary name-based lookup, while RetSpoofCall controls the visible return chain around the native protection call.

The patch routine also relies on the global gadget pointer Gdgt, declared externally in etw.h. That pointer must already identify a usable return-spoofing gadget when PatchETW() runs. Because the function performs no local null checks for the module handle, export addresses, native function pointer, or gadget, correct global initialization is a prerequisite.

Scope and Limitations

The implementation is narrowly targeted. It patches two ntdll exports and does not enumerate ETW providers, alter registrations, or install a general interception framework. The hard-coded hashes and three-byte offsets bind the behavior to the expected export layout and hashing algorithm. If a resolver returns an unexpected address or the target prologue changes, the pointer arithmetic can select the wrong byte. The code verifies only that the replacement byte was copied, not that the surrounding instructions match an expected signature.

Operationally, this stage should be understood as a small in-memory mutation composed from four existing primitives: hashed module lookup, hashed export parsing, return-address-spoofed calls, and native page-protection changes. It sits between ntdll restoration and payload materialization, and its state is process-local. Nothing is written back to disk, and no later routine restores the original ETW instruction bytes before process exit.

PAGE 15 · 3.4-Native Delay and Stack Concealment.md

Native Delay and Stack Concealment

The sleep-evasion path is built around cooperative Windows fibers. The payload executes on a dedicated fiber, while the original thread becomes a scheduler fiber. When payload code calls the patched Sleep entry point, control is redirected to FiberSwitcher(), which records the requested duration and switches back to the scheduler. The scheduler performs the wait from its own stack and then resumes the payload fiber. As a result, the payload's call stack remains suspended during the delay instead of remaining active inside the ordinary sleep implementation.

Fiber Roles

Ghost.cpp defines two global fiber pointers. InitialFiber represents the original program thread after conversion, while Creation stores the payload fiber returned by CreateFiber. The program installs the Sleep redirection before converting the current thread, then converts the thread with the resolved ConvertThreadToFiber pointer. After payload memory is changed to executable and readable, CreateFiber receives the payload address as its start routine.

graph TD Thread([Original thread]) --> Convert[Convert to initial fiber] Convert --> Create[Create payload fiber] Create --> Loop[Enter scheduler loop] Loop --> Payload[Switch to payload] Payload --> Sleep[Payload calls Sleep] Sleep --> Switcher[FiberSwitcher records delay] Switcher --> Loop Loop --> Wait[Native event wait] Wait --> Payload

The main loop has no termination condition. Each iteration switches to the payload fiber. Execution in the scheduler resumes only when the payload yields back, which the installed Sleep hook is designed to cause. The scheduler then calls DelayExecution(dwSleepTime) and repeats. If the payload returns normally instead of calling the hooked function, standard fiber semantics affect whether control can continue, so the intended lifecycle assumes repeated sleep calls.

Capturing the Requested Delay

FiberSwitcher uses an extern C signature with a DWORD first argument and a variadic tail. The first value corresponds to the millisecond duration expected by Sleep or the leading argument of a compatible sleep call. The function copies that value into the global dwSleepTime and then invokes the resolved SwitchToFiber function through RetSpoofCall, targeting InitialFiber.

The switch is synchronous from the payload fiber's perspective. Its stack is not destroyed; it remains allocated with execution paused inside FiberSwitcher at the point of the switch. When the scheduler later switches back to the payload fiber, execution continues after SwitchToFiber and FiberSwitcher returns to the payload's caller. This preservation of the suspended call chain is the mechanism behind the stack-concealment description. It is not stack encryption or stack erasure.

Native Event Wait

DelayExecution implements the actual delay without calling the hooked Sleep function. It creates an unnamed event using the resolved NtCreateEvent pointer and requests EVENT_ALL_ACCESS. The event begins nonsignaled. The routine then converts the requested milliseconds into the relative timeout representation used by NtWaitForSingleObject.

Windows native relative intervals use signed 100-nanosecond units. Multiplying milliseconds by 10,000 converts the value to those units, and negating the result marks it as a relative rather than absolute time. The resulting LARGE_INTEGER is passed to NtWaitForSingleObject with alertable waiting disabled. Because the newly created event is never signaled, the wait normally completes when the relative timeout expires.

graph TD Milliseconds([Requested milliseconds]) --> Store[Store global delay] Store --> Yield[Switch to scheduler fiber] Yield --> Event[Create nonsignaled event] Event --> Convert[Multiply by ten thousand] Convert --> Relative[Negate interval] Relative --> NativeWait[NtWaitForSingleObject] NativeWait --> Resume[Resume payload fiber]

Both native calls are made through the return-spoofing bridge using the global gadget pointer. Their function pointers are initialized in functions.h through hashed resolution from loaded modules. NtWaitForSingleObject is represented by a native signature accepting a handle, an alertable flag, and a timeout pointer. NtCreateEvent receives the output handle, access mask, optional attributes, event type value, and initial state.

Relationship to the Sleep Hook

HookFunction builds a thirteen-byte absolute jump sequence. It places the FiberSwitcher address into an immediate field, temporarily changes protection on the target Sleep bytes, copies the jump, and restores the previous protection. Therefore a later call to the beginning of Sleep transfers directly to FiberSwitcher. The hook does not preserve a trampoline containing displaced original instructions because the intended replacement never calls the original function.

The redirection and scheduler must be considered together. The hook alone would merely transfer into FiberSwitcher; without a valid InitialFiber, switching would be invalid. Conversely, the scheduler loop depends on payload sleep calls reaching the switcher so that control returns for the native wait. dwSleepTime is the small shared state that transfers the requested duration between the two fibers.

State and Failure Boundaries

The code assumes successful creation and switching. FiberSwitcher does not verify that InitialFiber or the resolved switch function is non-null. DelayExecution does not check the returned status from NtCreateEvent or NtWaitForSingleObject, and it does not close the event handle after the wait. Repeated sleep cycles can therefore accumulate handles. The multiplication also occurs before assignment to the signed interval, so unusually large DWORD durations depend on integer conversion behavior.

No synchronization protects dwSleepTime, but the design uses one thread cooperatively switching between two fibers, so only one side executes at a time. The value is written immediately before yielding and read immediately after the scheduler regains control. This would need redesign if multiple payload fibers or threads shared the hook.

Lifecycle Summary

The main thread becomes the stable scheduling context, and the decrypted payload runs on a separate fiber backed by its own saved register and stack state. A payload sleep call records its delay and yields to the scheduler. The scheduler waits on an unsignaled native event using a negative relative timeout, then re-enters the same payload fiber. This design relocates the active waiting call away from the payload stack while preserving the payload's execution state for the next cycle.

Payload Packaging and Build Workflow

Ghost's build process converts raw x64 shellcode into a Windows executable whose payload is encrypted and embedded as a resource. The Python entry point accepts a shellcode file, creates a fresh 256-bit AES key and 128-bit IV, applies block padding, encrypts the input in CBC mode, and writes the ciphertext to icon.ico. Despite the filename, this output is treated as opaque RCDATA rather than an image. The same generated key material is formatted as C byte arrays and substituted into Ghost.cpp so the runtime decryptor and packaged ciphertext remain paired.

Build-Time Payload Transformation

The builder performs a stateful source-and-artifact transformation. It reads the caller-supplied binary, produces ciphertext, rewrites the key and IV declarations in the C++ source, and relies on Resource.rc to bind icon.ico to resource identifier 101. resource1.h and rsrc.h provide the numeric definition and runtime retrieval side of that contract. Re-running the build with another payload changes both the resource bytes and the embedded key material, so artifacts from different runs must not be mixed.

flowchart TD A[x64 shellcode file] --> B[Generate AES key and IV] B --> C[Pad and encrypt with AES-CBC] C --> D[Write icon.ico ciphertext] B --> E[Rewrite arrays in Ghost.cpp] D --> F[Compile Resource.rc] E --> G[Compile Ghost.cpp]

Native Compilation Pipeline

The script expects a Linux-hosted cross-compilation environment with NASM, the MinGW resource compiler, and the MinGW C++ compiler at configured absolute paths. retaddrspoof.asm and syscalls.asm are assembled as Win64 objects. Resource.rc becomes Resource.o, and Ghost.cpp becomes Ghost.o using optimization-oriented flags, disabled stack protection, exceptions, and RTTI, plus static runtime libraries. The final link combines all four objects into build/Ghost.exe and strips unused or identifying material where the selected flags permit it.

flowchart LR R[retaddrspoof.asm] --> RO[retaddrspoof.o] S[syscalls.asm] --> SO[syscalls.o] C[Ghost.cpp] --> CO[Ghost.o] X[Resource.rc] --> XO[Resource.o] RO --> L[MinGW linker] SO --> L CO --> L XO --> L L --> E[build/Ghost.exe]

Operational Assumptions

The documented command is python3 build.py -i shellcode.bin. The builder creates the build directory when needed but otherwise assumes the cryptography package and cross-toolchain are already installed. It treats any compiler stderr output as failure and modifies Ghost.cpp in place when injecting key material. Developers should understand that coupling before automating repeated builds or preserving source cleanliness. Payload compatibility also extends beyond compilation: the runtime hook must match the sleep API used by the selected payload, so adapting a different beacon may require a source change before invoking the builder.

Source and Resource Materialization

The build does not merely compile existing files. It converts one shellcode input into two mutually dependent compiler inputs: encrypted bytes become a Windows resource, while the matching random AES key and IV become literal arrays in the C++ source. Those representations are generated together and must be compiled into the same executable. Materialization is therefore the boundary between payload encryption and the ordinary resource/C++ toolchain.

The script requires an x64 shellcode path, derives source and build paths from the current working directory, and fixes the locations of windres, NASM, and MinGW build.py. Its main sequence prepares the payload before compiling either affected input: assembly comes first, then shellcode/source preparation, resource compilation, C++ compilation, and linking build.py. This ordering ensures that the resource compiler sees fresh ciphertext and the C++ compiler sees its matching key material.

Two Outputs from One Encryption Operation

Ciphertext becomes an RCDATA input

aes_encrypt generates a 32-byte key and 16-byte IV, formats both as complete C++ array declarations, pads the shellcode to the AES block size, and encrypts it in CBC mode build.py. do_aes reads the selected payload as binary data and writes the encrypted result to icon.ico build.py. The extension is only a filename convention here; the produced file is opaque ciphertext, not an image produced by an icon encoder.

The name icon.ico is a hard-coded interface between Python and the resource script. Resource.rc includes the resource identifier header and binds this file to a raw-data resource Resource.rc. resource1.h defines the shared symbol IDR_RCDATA1 as numeric identifier 101 resource1.h. Because the resource type is RCDATA, the resource compiler can carry arbitrary encrypted bytes without interpreting their contents.

flowchart LR S[Required x64 shellcode] --> P[Python reads binary input] P --> E[AES-CBC encryption and padding] E --> C[icon.ico ciphertext] C --> R[Resource.rc binds IDR_RCDATA1 as RCDATA] R --> W[windres] W --> O[build/Resource.o]

build_resource() invokes x86_64-w64-mingw32-windres with Resource.rc as input and build/Resource.o as output. If the compiler writes a diagnostic to standard error, the script reports the command and stops build.py. During a full build, preparation has already created icon.ico. Running the resource compiler in isolation is different: the caller must ensure that the file exists and belongs to the intended payload generation.

Key material becomes C++ source

The other output is embedded by mutating Ghost.cpp. After encryption, prepare_src_shellcode() constructs regular expressions for complete AesKey and AesIv declarations, reads the source, substitutes the generated declarations, and writes the entire file back build.py. This is not a generated header, linker symbol, or command-line macro. The tracked source itself becomes a generated build input.

The replacement depends on exact textual anchors. Each pattern expects a one-line declaration shaped like unsigned char Name[] = { ... };. Renaming the variables, adding qualifiers, or splitting the declarations across lines can prevent a match. The current source provides the expected slots as a 32-byte AesKey array and a 16-byte AesIv array Ghost.cpp. The script does not check the number of substitutions, so it can print “Updated C++ src” even if a future source edit makes one pattern stop matching.

This behavior makes repeated builds non-reproducible and source-mutating. Every complete invocation generates fresh random bytes, overwrites icon.ico, and replaces both arrays. The resulting source remains modified after the build. A second build of the same shellcode therefore creates a different ciphertext/key/IV tuple, even though the logical input payload has not changed.

Resource Identity and Runtime Reunion

One symbolic ID joins the compiler and loader

The resource lookup code includes resource1.h, so it consumes the same IDR_RCDATA1 symbol as the resource script rsrc.h. GetFromRc calls the resolved FindResourceW interface with both MAKEINTRESOURCEW(IDR_RCDATA1) and RT_RCDATA rsrc.h. Both the numeric identity and the type must match the compiled declaration. Changing the ID or type on only one side produces a valid build artifact that runtime lookup cannot find.

After finding the entry, the helper loads it, locks it to obtain a pointer, and asks Windows for its exact size rsrc.h. It publishes the pointer and size through its reference parameters rsrc.h. The helper prints messages for null lookup, load, or lock results, but it does not return a distinct failure code or stop immediately. Consequently, an incorrectly materialized resource may surface later as a bad pointer or size rather than as a clean packaging failure.

Embedded bytes meet embedded key material

In main, the program calls GetFromRc, allocates a buffer using the reported resource size, and copies exactly that many bytes from the resource pointer Ghost.cpp. It then calls AESDecrypt with the copied ciphertext, resource length, and compiled-in AesKey and AesIv arrays Ghost.cpp. This call is the first runtime point at which the two separately compiled representations reunite.

sequenceDiagram participant B as build.py participant C as Ghost.cpp participant R as Resource.rc participant X as Executable participant D as Runtime decryption B->>B: Generate key, IV, and ciphertext B->>C: Replace AesKey and AesIv declarations B->>R: Write ciphertext to icon.ico R->>X: Embed bytes as IDR_RCDATA1 / RT_RCDATA C->>X: Compile key and IV into program data X->>D: Retrieve resource by ID and type D->>D: Use matching arrays to decrypt bytes

The central invariant is that both branches originate from the same aes_encrypt call. The resource alone contains no decryption key, and the arrays alone contain no payload. Compilation can succeed when the branches come from different runs, but runtime decryption will fail because CBC ciphertext is bound to its exact key and IV.

Ordering and Artifact Coupling

Preparation precedes both affected compilers

prepare_src_shellcode() first calls do_aes(SHELLCODE), which creates the ciphertext and initializes the formatted declaration strings. Only then does it rewrite Ghost.cpp build.py. Resource compilation follows, so windres sees the new icon.ico. C++ compilation follows that, so MinGW sees the new arrays and emits build/Ghost.o build.py. The later link consumes Resource.o and Ghost.o together build.py. Final link flags and executable layout are covered in the Linking and Payload Adaptation chapter; for materialization, the important fact is that both branches enter one output.

Generated value Intermediate representation Compiled consumer
AES ciphertext icon.ico Resource.o and GetFromRc
AES key AesKey[] in Ghost.cpp Ghost.o and AESDecrypt
AES IV AesIv[] in Ghost.cpp Ghost.o and AESDecrypt
Resource identity IDR_RCDATA1 = 101, type RCDATA Resource compiler and lookup helper

The resource size is not assumed from the original payload. Encryption pads the input, and runtime uses SizeofResource, so the copied ciphertext length matches the materialized resource rather than the pre-padding shellcode size.

Complete reruns are safe; partial reruns are risky

A full invocation refreshes both branches in the intended order. Partial or cached builds can silently mix generations:

  • Running preparation alone changes icon.ico and Ghost.cpp but leaves existing Resource.o and Ghost.o stale.
  • Running only resource compilation embeds whichever bytes currently occupy icon.ico, without proving that the source arrays match.
  • Running only C++ compilation captures the current arrays, without proving that the existing resource object belongs to them.
  • Reusing either object file bypasses the freshness relationship encoded by the full script.

The build writes no manifest, tuple identifier, or digest that connects the ciphertext to the arrays. Consistency is procedural: run the complete sequence without mixing objects from different invocations. The stable filename and resource ID simplify lookup, but they do not provide freshness checking.

Failure Boundaries and Safe Adaptation

Coupled names must change together

Adapting the materialization scheme requires updating every participant in a coupling. Changing the ciphertext filename requires changing both the Python output and the resource script. Renaming IDR_RCDATA1 or changing its numeric value requires consistent edits in Resource.rc, resource1.h, and the lookup code. Renaming or reshaping the key arrays requires changing the regex replacements and the runtime decryption arguments. The current grep-visible chain is intentionally small: build.py creates icon.ico and array declarations, Resource.rc binds the file, resource1.h defines the ID, rsrc.h finds it, and Ghost.cpp passes the arrays to decryption.

A robust extension would verify that each source substitution occurred exactly once and could attach a shared digest or generation marker to the two compiled branches. Those checks are not implemented, so documentation and disciplined full builds are the current safeguards.

Scope limits

This stage ends after creation of matching source and resource compiler inputs. AES provider internals, randomized memory placement, fiber scheduling, assembly compilation details, and payload-specific Sleep-hook behavior belong to their dedicated chapters. Materialization only explains how encrypted bytes and their key material are made concrete and how the compiled program locates the correct resource.

The practical rule is to treat icon.ico, the generated declarations, Resource.o, and Ghost.o as one generation. The build script enforces that relationship through ordering, not metadata. Following the complete sequence preserves the invariant; isolated manual steps can produce an executable that links successfully yet cannot decrypt its embedded payload.

PAGE 20 · 4.4-Linking and Payload Adaptation.md

Linking and Payload Adaptation

The final build step turns four independently produced object files into one Windows executable, but successful linking is only the mechanical half of payload integration. A payload must also match the loader's x64 execution model and its assumption that a particular delay API can be redirected into the fiber scheduler. The build script can accept any file supplied through --shellcode, yet the resulting executable is operationally compatible only when the embedded bytes and runtime control-flow expectations agree.

The documented build entry point is python3 build.py -i shellcode.bin, and the repository states that compilation is performed on Linux with the MinGW suite README.md. The script reinforces that constraint with absolute paths for x86-64 MinGW, windres, and NASM, and describes the required input as x64 shellcode build.py. Consequently, adaptation begins with the correct architecture and toolchain before considering the payload's behavior.

Final Link Composition

Four objects form one executable

The link command invokes the x86-64 MinGW C++ driver with four explicit inputs, in this order:

  1. build/syscalls.o
  2. build/retaddrspoof.o
  3. build/Resource.o
  4. build/Ghost.o

The command appends MinGW_LINK_FLAGS and writes build/Ghost.exe build.py. There is no library archive or intermediate executable layer. The final PE therefore combines the two NASM support objects, the compiled resource object, and the main C++ translation unit directly.

flowchart TD SA[syscalls.asm] --> SO[build/syscalls.o] RA[retaddrspoof.asm] --> RO[build/retaddrspoof.o] RC[Resource.rc plus encrypted payload] --> RCO[build/Resource.o] GC[Ghost.cpp plus generated key and IV] --> GO[build/Ghost.o] SO --> L[x86_64-w64-mingw32-g++ link] RO --> L RCO --> L GO --> L L --> EXE[build/Ghost.exe]

Each object supplies a distinct part of the executable contract. syscalls.o provides the assembly entry points used by native-call wrappers. retaddrspoof.o supplies the return-address-spoofing bridge called throughout the C++ code. Resource.o carries the encrypted payload bytes. Ghost.o supplies the program entry point, generated AES arrays, orchestration logic, and header-defined helper implementations. Removing an object is not an optional size optimization; it leaves referenced code or resource data unavailable.

The build order creates these objects before linking. NASM emits the two win64 objects, windres emits Resource.o, and MinGW compiles Ghost.cpp into Ghost.o build.py. The C++ compile command is separate from the link command and uses -c, so compile flags and link flags have different scopes build.py. Changes intended to affect final linking belong in MinGW_LINK_FLAGS, not only in MinGW_FLAGS.

Link policy and output characteristics

The link flags enable link-time optimization, merge constants, request inlining and other optimizations, disable the stack protector, exceptions, RTTI, and loop unrolling, suppress symbols, garbage-collect unused sections, strip the output, and statically link the GCC and C++ support runtimes build.py. These settings favor a compact, self-contained artifact with fewer runtime toolchain dependencies. They also reduce debugging visibility: stripping and suppressed diagnostics make symbol-level investigation more difficult, while disabled exception and RTTI support constrain C++ features that adaptations can safely introduce.

The script creates build/ if it is absent but reuses it when present build.py. Its visible products are the four object files and build/Ghost.exe; the encrypted icon.ico remains in the working directory because it is generated as a resource input rather than a build-directory output. The script does not delete stale objects before compiling and does not emit a dependency manifest. A complete successful invocation refreshes every required object, but manual or interrupted builds can leave a mixed set of artifacts.

Source-Mutating Build Consequences

The executable depends on the current source generation

Before Ghost.o is compiled, the builder encrypts the selected payload and replaces the literal AesKey and AesIv declarations inside Ghost.cpp build.py. The resource compiler separately embeds the matching ciphertext. The final link is therefore meaningful only when Resource.o and Ghost.o originate from the same preparation pass.

This coupling is not represented in filenames. Every run still produces Resource.o, Ghost.o, and Ghost.exe, even though random key material changes. A stale resource object can link cleanly with a freshly compiled main object, and the reverse is also possible. In either case, the executable is structurally valid but decryption will fail at runtime. The safest workflow is to run the full script for each payload and treat all generated artifacts as one indivisible generation.

The source mutation also affects repository hygiene. Building changes Ghost.cpp in place and leaves the latest key and IV visible in the working tree. This is intentional behavior, not a compiler side effect. Developers should expect a dirty source file after a build, should avoid committing generated secrets accidentally, and should not assume two builds from the same checkout are byte-for-byte reproducible. The existing script does not restore placeholder arrays after linking.

Failures are stage-oriented, not transactional

Every subprocess captures standard error and exits when standard error is nonempty. The link failure message prints the exact command, although its text says the C++ object build failed even when the failing operation is linking build.py. Earlier stages may already have overwritten source and artifacts when a later step fails. Retrying only link() is appropriate only if all four objects are known to be current and mutually consistent; otherwise, rerunning the complete script is safer.

Payload Execution Contract

Shellcode is entered as a fiber routine

After decrypting and placing the payload, Ghost.cpp changes the allocated region to executable-read protection and passes the payload address to CreateFiber as an LPFIBER_START_ROUTINE Ghost.cpp. This is more specific than “execute arbitrary bytes.” The input must be x64 code compatible with the Windows environment and capable of running from the address selected by the loader. Position-dependent payloads, payloads built for another architecture, or code that assumes a different entry convention are incompatible even though encryption and linking can still succeed.

The host thread is converted to the initial fiber, the payload fiber is created, and an infinite loop repeatedly transfers control to it Ghost.cpp. When control returns to the initial fiber, the loop performs the recorded delay and switches back again Ghost.cpp. Payload adaptation must preserve this handoff model. The executable is not simply calling a function once and waiting for it to return; it expects cooperative switching around sleep periods.

The default hook assumes kernel32 Sleep behavior

The current program installs HookFunction(Sleep, FiberSwitcher) before starting the payload fiber Ghost.cpp. The README explains the intended case: for a Cobalt Strike beacon, kernel32!Sleep is replaced with fiber switching so the beacon call stack is hidden during the sleep period README.md. This assumption is payload-specific rather than a general property of shellcode.

HookFunction constructs a 13-byte absolute jump, inserts the redirection address into that stub, temporarily changes the target region to writable memory, copies the patch into the target API, and restores the previous protection hook.h. FiberSwitcher interprets its first argument as a millisecond delay, stores it in the global dwSleepTime, and switches to InitialFiber hook.h. The main loop then calls DelayExecution(dwSleepTime), which creates an event and waits through NtWaitForSingleObject using a relative interval derived from the milliseconds hook.h.

This creates several adaptation requirements:

  • The payload must actually reach the patched API during its delay behavior. A payload that sleeps through another API will not trigger the handoff.
  • The replacement target's calling convention and arguments must match what the redirection function expects. The current handler assumes its first argument is a DWORD duration in milliseconds.
  • The target must tolerate replacement of its first 13 bytes with the absolute jump sequence.
  • The payload must remain valid while suspended as a fiber and resume correctly after the main fiber finishes the native wait.
  • If the payload never enters the hook, the main fiber does not regain control through the intended sleep path.

The README recommends observing another beacon's API behavior with a monitoring tool, identifying the actual function used for sleeping, and replacing the hook target in Ghost.cpp. It specifically notes that a NightHawk-style payload may require hooking one of the thread-pool creation APIs instead of Sleep README.md. That example also shows why adaptation is more than swapping one symbol: a thread-pool API has different parameters and semantics, so the redirection handler and scheduler may need corresponding changes.

Adaptation Checklist

Keep the build and runtime assumptions aligned

A payload change is complete only when both packaging and runtime behavior have been checked. The following sequence reflects the repository's actual constraints:

  1. Produce x64 position-appropriate shellcode and invoke the full Linux build command rather than linking cached objects.
  2. Confirm that preparation regenerated both ciphertext and the source arrays before Resource.o and Ghost.o were compiled.
  3. Preserve all four link inputs unless their exported or referenced functionality has been deliberately replaced.
  4. Determine which delay mechanism the payload actually uses; do not assume every beacon calls kernel32!Sleep.
  5. If the hook target changes, adapt the redirection function's signature, argument extraction, and delay semantics as a unit.
  6. Verify that the payload can execute as a fiber start routine and repeatedly resume after the loader's wait cycle.
  7. Rebuild from the complete script after source changes so that generated objects and the final executable are consistent.

This chapter intentionally stops at the integration boundary. Detailed assembly conventions, inline-hook implementation mechanics, AES/resource construction, and fiber scheduling internals are covered elsewhere. For linking and adaptation, the decisive point is that build/Ghost.exe combines a fixed set of x64 objects with a payload-dependent runtime contract. A successful link proves that symbols and object formats agree; it does not prove that the payload uses the expected sleep API or cooperates with the fiber lifecycle.
