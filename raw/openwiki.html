Loader Pipeline (End-to-End Execution Flow)

Ghost is a standalone evasive Windows shellcode loader. Its entire runtime is orchestrated from main() in Ghost.cpp, which calls nearly every evasion mechanism in a strict sequence. Understanding this order — and how the heap-staged plaintext shellcode transitions into a fiber-hosted, executing beacon — is the key to reading the whole project.

Two repository-level invariants make the pipeline readable:

  • RetSpoofCall is the universal call wrapper. Nearly every API, NT call, and indirect syscall in the project is invoked through RetSpoofCall(Function, nArgs, Gdgt, ...). It marshals the target function's real arguments, places a ROP gadget as the return address, and lets the target function return through it, so the true caller never appears on the stack during EDR unwinding. It is described in depth on the return-address-spoofing page.
  • Gdgt is the shared ROP gadget pointer. Declared in Ghost.cpp as PVOID Gdgt = FindROPGadget(); and extern'd across allocator.h, hook.h, etw.h, unhook.h, rsrc.h, and AES.h, the same randomly-chosen call r12 gadget from ntdll is threaded through every spoofed call. This keeps one consistent gadget as the return-target across all modules.

Startup Sequence in main()

main() runs the loader in two phases: first it stages decrypted payload in hidden memory, then it converts the thread to fibers and executes it. The verified order is:

flowchart TD A["main() entry"] --> B["FlushNTDLL()"] B --> C["PatchETW()"] C --> D["GetFromRc(ResourceSize, ptr)"] D --> E["RetSpoofCall(memcpy) ciphertext to heap"] E --> F["AESDecrypt(AesCipherText,...)"] F --> G["allocate_large_page(PlainBufferSize)"] G --> H["place_data_rand(pLPI, plaintext, size)"] H --> I["free(AesCipherText) + delete plaintext"] I --> J["HookFunction(Sleep, FiberSwitcher)"] J --> K["ConvertThreadToFiber -> InitialFiber"] K --> L["NtProtectVirtualMemory PAGE_EXECUTE_READ"] L --> M["CreateFiber(entry = pLPI->lpData) -> Creation"] M --> N["SwitchToFiber loop"]

Startup sequence of main(): unhook, patch ETW, load+decrypt the resource, hide the payload in a large random allocation, install the Sleep hook, and set up the fiber pair.

1. FlushNTDLL()

The first call removes EDR hooks from ntdll by creating a suspended audiodg.exe, reading a clean ntdll image from it via the SysNtReadVirtualMemory indirect syscall, and copying the clean .text section back over the local copy. Details live on the ntdll-unhooking page.

2. PatchETW()

Disables Event Tracing for Windows by overwriting NtTraceEvent and NtTraceControl in ntdll with an early ret (0xC3), after making their image writable with NtProtectVirtualMemory. All protection and memcpy operations are ret-spoofed. See etw-patching.

3. GetFromRc() + AES decryption

GetFromRc() (in rsrc.h) pulls the AES-encrypted shellcode out of the IDR_RCDATA1 RCDATA resource using FindResourceW → LoadResource → LockResource → SizeofResource (all hash-resolved in functions.h, all ret-spoofed). main() copies the resource bytes into a heap buffer and calls AESDecrypt() with the hardcoded 32-byte key and 16-byte IV (regenerated per build by build.py). The decrypt path runs the full BCrypt chain — BCryptOpenAlgorithmProvider, BCryptGetProperty, BCryptSetProperty (CBC), BCryptGenerateSymmetricKey, and a two-pass BCryptDecrypt — every call wrapped in RetSpoofCall. See shellcode-encryption-and-hiding.

4. Allocation and payload hiding

allocate_large_page() (in allocator.h) allocates a very large region sized ALIGN_PAGE(PlainBufferSize * FACTOR) with FACTOR = 2048, fills it with random cryptographic noise via SystemFunction036 (RtlGenRandom), and picks a random byte offset within the block. place_data_rand() then copies the decrypted plaintext into that random slot. This is the Roshtyak camouflage technique used to defeat memory scanning. The decrypted heap buffer and ciphertext copy are freed immediately (free(AesCipherText) and delete[] pPlainBuffer) so the plaintext exists only inside the camouflaged allocation.

5. Hook Sleep and set up fibers

HookFunction(Sleep, FiberSwitcher) installs a 13-byte trampoline hook (mov r10, imm64 / jmp r10) over Sleep so that any call the beacon makes to Sleep diverts to FiberSwitcher. Then:

  • ConvertThreadToFiber turns the current loader thread into InitialFiber.
  • NtProtectVirtualMemory flips the large page to PAGE_EXECUTE_READ, making the staged payload executable.
  • CreateFiber(NULL, (LPFIBER_START_ROUTINE)pLPI->lpData, NULL) creates the Creation fiber whose start routine is the decrypted, now-executable shellcode (pLPI->lpData).

All three of these calls are ret-spoofed. The NtProtectVirtualMemory result is checked with NTAPI_VALIDATE_RETURN2NULL(NtProtect_MAIN, status), so a failure returns NULL from main.

The Fiber Switching Sleep Cycle

Once both fibers exist, main() enters an infinite loop that alternates between running the payload fiber and sleeping the loader thread:

sequenceDiagram participant M as main (InitialFiber) participant P as PayloadFiber (lpData) participant S as Sleep hook / FiberSwitcher participant D as DelayExecution loop while true M->>P: SwitchToFiber(Creation) Note over P: payload/beacon runs P->>S: calls Sleep(dwMilliseconds) S->>S: stores dwSleepTime S->>M: SwitchToFiber(InitialFiber) Note over M: beacon stack hidden M->>D: DelayExecution(dwSleepTime) Note over D: NtCreateEvent + NtWaitForSingleObject D-->>M: returns after delay end

The fiber switching sleep cycle: the payload fiber runs until it calls Sleep, the hook switches back to the loader fiber, the loader performs a kernel-invisible event-based delay, then control returns to the payload.

The loop in main() first calls RetSpoofCall(e_SwitchToFiber, 1, Gdgt, Creation) to hand control to the payload fiber and execute the beacon. When the beacon calls Sleep, the hook redirects to FiberSwitcher (in hook.h), which:

  1. Records the requested duration in the global dwSleepTime so the real sleep can be reproduced later.
  2. Switches back to InitialFiber via RetSpoofCall(e_SwitchToFiber, 1, Gdgt, InitialFiber).

Because fibers are userland-only execution units, neither fiber switch nor the sleeping state emits kernel callbacks, and the beacon's entire call stack disappears from the thread stack while it is not running. Control returns to main() after the SwitchToFiber at the top of the loop returns; main() then calls DelayExecution(dwSleepTime) to actually sleep. DelayExecution (in hook.h) creates an event with NtCreateEvent and waits on it with NtWaitForSingleObject using a negated relative timeout — both ret-spoofed — so the loader thread blocks without the beacon visible on the stack. The loop then repeats.

The Sleep hooking assumes a Cobalt Strike-style beacon that sleeps via kernel32!Sleep. For other C2 frameworks the README notes a different sleep API (e.g., one of NightHawk's CreateThreadPool APIs) must be hooked instead; the pipeline is identical otherwise.

Error Handling and Constants

The project composes error handling and fake handles from defs.h, which every module includes:

  • SELF_HANDLE = (HANDLE)-1 — pseudo-handle passed as the process handle to NT VM APIs, meaning "the current process". It is threaded through NtAllocateVirtualMemory, NtProtectVirtualMemory, and the indirect syscalls.
  • CURRENT_THREAD = (HANDLE)-2 — pseudo-handle for the current thread, available for thread-targeted NT calls.
  • NTAPI_VALIDATE_RETURN, NTAPI_VALIDATE_RETURN2VOID, and NTAPI_VALIDATE_RETURN2NULL — all three check an NTSTATUS != 0 and print {!!} <API> failed with status: <hex>, differing in the return value on failure: -1, void (bare return), or NULL respectively. main() uses NTAPI_VALIDATE_RETURN2NULL(NtProtect_MAIN, status) after flipping the large page; allocate_large_page uses the same macro after NtAllocateVirtualMemory; HookFunction and PatchETW use the 2VOID variant.
  • NTAPI_ERR, HANDLE_ERROR, and PRINT are additional logging helpers, and _DEBUG_PRINT toggles all debug std::cout output at compile time (it is defined by default in defs.h).

These macros keep the failure semantics uniform across modules without relying on GetLastError for NT statuses, which is why NT calls are validated directly against their returned NTSTATUS.

Failure Semantics

  • If AESDecrypt fails, main() prints [+] Decryption UnSuccessful and returns -1 before any allocation or fiber setup.
  • If allocate_large_page cannot allocate, it returns NULL (via NTAPI_VALIDATE_RETURN2NULL), and the pipeline aborts.
  • If the NtProtectVirtualMemory making the page executable fails, main() returns NULL.
  • Because each step depends on the previous one's side effects (decrypted buffer → large page → executable fiber entry point), a failure at any step halts the loader before the payload fiber is ever scheduled.

Shared Types, Structures & Constants (structs.h, types.h, defs.h)

Ghost is an evasive shellcode loader whose modules (unhook.h, etw.h, allocator.h, hook.h, rsrc.h, AES.h, ntprocessapi.h, and Ghost.cpp) all depend on a small set of shared headers. This page documents the reusable types, NT structures, function-pointer typedefs, and compiler macros that those modules rely on. Nearly everything here is custom because the loader deliberately avoids importing most Windows SDK definitions and instead re-declares the low-level types it needs (or relies on hashed dynamic resolution rather than static linking).

Three headers together form this foundation:

  • structs.h — custom re-declarations of NT kernel-user structures (PEB, LDR, process parameters) and everything needed to call NtCreateUserProcess directly (PS_ATTRIBUTE_LIST, PS_CREATE_INFO, OBJECT_ATTRIBUTES, USTRING).
  • types.h — function-pointer typedefs for every dynamically resolved API, plus the extern "C" prototypes of the indirect syscall wrappers assembled in syscalls.asm.
  • defs.h — small compile-time macros and constants used as a shared vocabulary across modules.

Relationship to the rest of the project

These headers sit at the bottom of the dependency graph. types.h includes both structs.h and defs.h, and functions.h includes types.h and instantiates the actual function-pointer globals by hash-resolution. That one module (functions.h) is the single bridge that turns the typedefs into live GetFunctionAddressH-resolved function pointers, which every other module then calls — almost always through RetSpoofCall.

The custom NT structures in structs.h

Ghost cannot rely on the public Windows SDK exposing the internal layouts it needs (or wants to keep explicit), so structs.h re-declares them with the P... pointer aliases. The header opens by re-declaring RTL_HEAP_ENTRY (credited to AceLdr), a heap-entry structure whose DataAddress/DataSize fields are used to walk the process heap when locating an in-memory payload region.

PEB and loader types

The process environment block and loader structures are the ones an EDR-aware loader inspects or walks. Their comments cite the Windows Internals book and Process Hacker sources:

  • PEB_LDR_DATA — the loader data block: InLoadOrderModuleList, InMemoryOrderModuleList, and InInitializationOrderModuleList are the three LIST_ENTRY module lists that code walks to enumerate loaded modules (e.g. to find ntdll by name).
  • PEB — the process environment block. Notable fields include BeingDebugged (the classic debugger check), the BitField union (IsProtectedProcess, IsAppContainer, IsProtectedProcessLight, etc.), ImageBaseAddress, and Ldr (pointer to PEB_LDR_DATA). This is a deliberately partial declaration (the trailing //... indicates the remaining fields are omitted).
  • LDR_DATA_TABLE_ENTRY — one entry in the loader module lists: DllBase, EntryPoint, SizeOfImage, FullDllName, BaseDllName. Walking InLoadOrderModuleList and matching BaseDllName is how the resolver locates ntdll by hash (see resolvers.h/GetLoadedDllHandleH).

The USTRING struct (a local DWORD/PVOID variant of UNICODE_STRING) is the buffer carrier used by the RC4 init macros in defs.h.

NtCreateUserProcess datatypes

The loader creates a suspended sacrificial process (audiodg.exe) to harvest a clean ntdll, and it does so with a direct call to NtCreateUserProcess rather than the Win32 CreateProcess. That requires a full set of NT datatypes that structs.h provides:

  • RTL_USER_PROCESS_PARAMETERS and the RTL_USER_PROCESS_PARAMETERS_NORMALIZED flag (0x01) — built with RtlCreateProcessParametersEx before spawning.
  • CURDIR / RTL_DRIVE_LETTER_CURDIR and RTL_MAX_DRIVE_LETTERS (32) — the current-directory and per-drive current-directory records embedded in process parameters.
  • PS_ATTRIBUTE / PS_ATTRIBUTE_LIST — the attribute mechanism passed to NtCreateUserProcess. The PS_ATTRIBUTE_NUM enum lists every attribute (PsAttributeParentProcess, PsAttributeImageName, PsAttributeMitigationOptions, ...). PsAttributeValue(Number, Thread, Input, Additive) is the macro that packs a number plus the thread/input/additive flags (PS_ATTRIBUTE_THREAD 0x10000, PS_ATTRIBUTE_INPUT 0x20000, PS_ATTRIBUTE_ADDITIVE 0x40000, PS_ATTRIBUTE_NUMBER_MASK 0xffff) into the 64-bit Attribute field. In ntprocessapi.h, PS_ATTRIBUTE_IMAGE_NAME = PsAttributeValue(PsAttributeImageName, FALSE, TRUE, FALSE) selects the input-only image-name attribute, so the loader can tell NtCreateUserProcess which executable to create suspended.
  • PS_PROTECTION/PS_PROTECTED_TYPE/PS_PROTECTED_SIGNER — the protected-process levels (used with ProcessProtectionInformation).
  • PS_CREATE_INFO / PS_CREATE_STATE — the union that receives the outcome of NtCreateUserProcess: InitialState carries input init-flags (WriteOutputOnExit, DetectManifest, etc.), and SuccessState carries the resulting FileHandle, SectionHandle, PebAddressNative, and UserProcessParametersNative. The caller initializes CreateInfo.Size and CreateInfo.State = PsCreateInitialState before the call (see NtCreateUserSuspendedProcess).
  • OBJECT_ATTRIBUTES — re-declared so optional object-attributes parameters can be passed by the syscall signatures.

PROCESSINFOCLASS enum

structs.h also carries the full PROCESSINFOCLASS enum (a commented list of ~110 process-info classes with their query/set directions and value types). It is referenced when calling NtQueryInformationProcess-style queries such as ProcessDebugPort or ProcessDebugObjectHandle.

Function-pointer typedefs in types.h

Because nearly every imported function is resolved at runtime by hash (never linked by import table), types.h declares a heterogeneous set of function-pointer typedefs whose signatures match the real APIs. These are grouped by target module:

  • ntdll NT APIs — fNtAllocateVirtualMemory, fNtWriteVirtualMemory, fNtReadVirtualMemory, fNtProtectVirtualMemory (the memory manipulation used by the allocator, ETW patching, and unhooking), plus fnNtWaitForSingleObject, fNtCreateEvent, and the RtlCreateProcessParametersEx / RtlInitUnicodeString helpers used to build process parameters.
  • kernelbase APIs — fnConvertThreadToFiber, fnCreateFiber, fnSwitchToFiber (the fiber machinery in Ghost.cpp and hook.h), and the resource helpers fnFindResourceW, fnLoadResource, fnLockResource, fnSizeofResource (used by rsrc.h/GetFromRc for IDR_RCDATA1).
  • BCrypt AES APIs — fnBCryptOpenAlgorithmProvider, fnBCryptGetProperty, fnBCryptSetProperty, fnBCryptGenerateSymmetricKey, fnBCryptDecrypt, fnBCryptDestroyKey, fnBCryptCloseAlgorithmProvider, consumed by AES.h's decryption chain.

Each typedef is the contract for the global function pointer of the same name declared in functions.h, which resolves it with GetFunctionAddressH(hModule, hash). So the typedefs and the functions.h globals are two halves of the same hashed-resolution design — the typedef defines the call signature, and functions.h supplies the address.

Indirect syscall extern declarations

In addition to resolved direct calls, the loader performs indirect syscalls to evade userland hooks on the most critical operations. types.h declares the prototypes with extern "C" (C linkage so the assembly can reference them by the plain symbol names):

  • SysNtCreateUserProcess — the 11-argument process/thread spawn that underlies ntprocessapi.h's NtCreateUserSuspendedProcess.
  • SysNtReadVirtualMemory — reads a clean ntdll image out of the suspended process in unhook.h.
  • SysNtProtectVirtualMemory — flips page protections during unhooking and payload staging.
  • SysNtTerminateProcess — closes the sacrificial helper process after its ntdll is read.

These Sys* names are implemented in syscalls.asm (NASM syntax), which loads the per-syscall SSN (dwNt*) and the syscall address (sysCallNt*) and jumps into ntdll's syscall stub to avoid executing the first bytes of the hooked function. The SSN/address pairs are themselves filled by GetSysCallByWalking in functions.h. This is the boundary where types.h (the C/C++ contract) meets the raw assembly layer, and it is what the indirect-syscalls and ntdll-unhooking pages build on.

Macros and constants in defs.h

  • SELF_HANDLE ((HANDLE)(-1)) and CURRENT_THREAD ((HANDLE)(-2)) — the NT pseudo-handles for the current process and current thread, passed as the first argument to NtAllocateVirtualMemory, NtProtectVirtualMemory, etc. across allocator.h, unhook.h, etw.h, and hook.h.
  • HANDLE_ERROR(FUNCTION, ERROR_MSG) — prints a function name plus a message literal.
  • NTAPI_ERR(NTAPI, status) — prints {!!} <name> failed with status: <hex>.
  • PRINT(DATA) and API_ERR(API) — general output helpers (API_ERR prints GetLastError()).
  • NTAPI_VALIDATE_RETURN(...) — checks an NTSTATUS against 0 (STATUS_SUCCESS) and, on failure, prints the name and hex status and returns -1; the NTAPI_VALIDATE_RETURN2VOID and NTAPI_VALIDATE_RETURN2NULL variants return void and NULL respectively. These are the project's primary NT error-handling pattern, used heavily in etw.h (e.g. NTAPI_VALIDATE_RETURN2VOID(NtProtectControl, ...)).
  • InitializeRC4EncryptionDecryptionData / InitializeRC4EncryptionDecryptionKey — two macros that zero and populate a USTRING (Buffer, Length, MaximumLength) from buffer+length, intended to initialize RC4 data/key string structures.
  • _DEBUG_PRINT — a compile-time toggle: it is #defined by default, and comments instruct that undefining it removes diagnostic std::cout print statements at compilation. The #ifdef _DEBUG_PRINT guards in unhook.h, etw.h, Ghost.cpp, allocator.h, and rsrc.h all turn their [DEBUG] ... chatter on and off through this single switch.

The RCDATA1 resource identifier (Resource.rc / resource1.h)

resource1.h is the Visual C++ generated header behind Resource.rc. It defines:

  • IDR_RCDATA1 (101) — the identifier used to embed the AES-encrypted shellcode.

Resource.rc contains a single line, IDR_RCDATA1 RCDATA "icon.ico", which binds IDR_RCDATA1 to a custom RCDATA resource whose bytes are read from the file icon.ico. At runtime rsrc.h's GetFromRc() retrieves that payload by calling FindResourceW(NULL, MAKEINTRESOURCEW(IDR_RCDATA1), RT_RCDATA) → LoadResource → LockResource → SizeofResource, then hands the bytes to AESDecrypt in main() for decryption before staging. Together this lets the loader carry its encrypted shellcode as a data resource rather than in a plain import/global — the same resource that build.py regenerates (along with the AES key/IV) for each build.

The combined data flow that ties these shared definitions together:

flowchart TD A["types.h: Sys* prototypes"] --> B["syscalls.asm: NASM indirect syscall thunks"] B --> C["functions.h: GetSysCallByWalking fills SSN + addr"] A --> D["functions.h: hash-resolved function-pointer globals"] D --> E["RetSpoofCall wrapped calls"] F["resource1.h: IDR_RCDATA1 = 101"] --> G["Resource.rc: RCDATA from icon.ico"] G --> H["rsrc.h: GetFromRc() loads resource"] I["structs.h: PS_ATTRIBUTE_LIST / PS_CREATE_INFO / RTL_USER_PROCESS_PARAMETERS"] --> J["ntprocessapi.h: NtCreateUserSuspendedProcess"] J --> B H --> K["etw.h / unhook.h / allocator.h / hook.h use SELF_HANDLE + NTAPI_VALIDATE_RETURN* from defs.h"]

How the shared types drive module behavior: typedefs become resolved globals, the Sys* prototypes bind to assembly syscall thunks, the resource identifier feeds the loader's payload, and defs.h macros standardize handle and error handling everywhere.

Invariants and failure semantics

  • Error handling is consistent by return convention. Every NT call that matters funnels through either the explicit NTAPI_VALIDATE_RETURN* macros (which abort the enclosing function with -1/void/NULL on non-zero status) or an explicit status != ERROR_SUCCESS comparison that prints a hex status and returns early (as in unhook.h, ntprocessapi.h).
  • Only the Sys* indirect syscalls are extern "C". Direct-called APIs are resolved as typed globals in functions.h; only the four assembly-backed syscalls need C linkage so syscalls.asm can reference their symbols directly.
  • The resource and the crypto key/IV are per-build artifacts. IDR_RCDATA1 always names the payload resource, but its bytes (icon.ico) and the AES key/IV used to decrypt it are regenerated per build by build.py, so the shared types stay stable while the secrets change.
  • These headers are contract-only; they hold no global state. structs.h/types.h/defs.h declare types and macros, and the actual initialized globals (functions.h's pointers, the dwNt*/sysCallNt* SSN pairs, Gdgt, rc4key, etc.) live in implementation modules. Any module that wants to call into this machinery includes functions.h rather than the type headers alone.

API Resolution & Custom Hashing (resolvers.h, hash.h, functions.h)

Ghost avoids static linking and import-table references almost entirely. Instead of letting the loader build an import address table that security tooling can scan, it resolves every module base and every function address at runtime by hashing a string and matching it against values computed from in-memory metadata. This page documents the custom hash function, the PEB-based module lookup, the PE export-directory function lookup, and the SSN/decoy resolution that feeds the indirect syscall layer.

Three headers cooperate to make this work:

  • hash.h — WEIRDHASHA and its helper getStringAsDWORD, the string-hashing primitive every resolver depends on.
  • resolvers.h — GetLoadedDllHandleH (module lookup by walking the PEB loader lists), GetFunctionAddressH (function lookup by parsing a module's IMAGE_EXPORT_DIRECTORY), GetSysCallByWalking (SSN + decoy syscall resolution), and IsHooked (syscall-prologue hook detection). It also carries name-based variants (GetLoadedDllHandleByName, GetFunctionAddressByName) used by the unhooking logic.
  • functions.h — the central registry: it instantiates every resolved HMODULE and function-pointer global by evaluating the resolver functions at load, and it declares the SSN and decoy-address variables that syscalls.asm consumes.

structs.h supplies the PEB / PEB_LDR_DATA / LDR_DATA_TABLE_ENTRY layouts that resolvers.h walks (see shared-types-and-constants).

The WEIRDHASHA hash primitive (hash.h)

WEIRDHASHA is the single string-hash used for both module and function lookup. Its signature is DWORD WEIRDHASHA(const char* String, SIZE_T Iterations), where Iterations controls how many times the base hash is folded.

DWORD WEIRDHASHA(_In_ const char* String, SIZE_T Iterations) {
    SIZE_T Index = 0;
    DWORD Hash = 5381;           // starting seed
    SIZE_T Length = Iterations;

    while (Index != Length) {    // fold multiply exactly Iterations times
        Hash = (Hash << 5) + Hash;   // Hash * 33
        Index++;
    }

    DWORD dwString = getStringAsDWORD(String);   // hash of the string characters
    return Hash * dwString + lstrlenA(String);   // multiply by string-DWORD, add length
}

The algorithm:

  1. Seed the accumulator at 5381.
  2. Fold Hash * 33 ((Hash << 5) + Hash) exactly Iterations times. The caller chooses this count, so the same string hashes differently depending on context — GetLoadedDllHandleH uses 28 iterations for module names and GetFunctionAddressH uses 27 for function names.
  3. Compute getStringAsDWORD(String), which walks the whole string accumulating value = (value << 5) + value + str[i] (i.e. value * 33 + char), starting from 0.
  4. Return Hash * dwString + lstrlenA(String).

The multiply-by-dwString plus the string length makes the hash highly specific to both content and length, so a hardcoded numeric constant in the source unambiguously identifies one export or module. Because these constants are baked into functions.h, they are only valid as long as the running Windows build's export names and module full-names hash to the same values — a point the loader already accepts since it targets the standard ntdll/kernelbase exports.

Resolving a module base: GetLoadedDllHandleH (PEB walking)

GetLoadedDllHandleH(DWORD dwHash) returns an HMODULE by walking the InLoadOrderModuleList of the process loader data, instead of calling GetModuleHandle/LoadLibrary. It works because every loaded module already has a LDR_DATA_TABLE_ENTRY whose FullDllName.Buffer is a wide path string.

PPEB peb = reinterpret_cast<PPEB>(__readgsqword(96));          // TEB->ProcessEnvironmentBlock
PPEB_LDR_DATA ldr = reinterpret_cast<PPEB_LDR_DATA>(peb->Ldr);
PLDR_DATA_TABLE_ENTRY ldte = ... ldr->InLoadOrderModuleList.Flink;

while (true) {
    // copy FullDllName.Buffer into a CHAR ANSI[] buffer
    DWORD Hash = WEIRDHASHA(ANSI, 28);
    if (dwHash == Hash) return reinterpret_cast<HMODULE>(ldte->DllBase);
    ldte = ... ldte->InLoadOrderLinks.Flink;   // next module in load order
}

Mechanics worth noting:

  • __readgsqword(96) reads the x64 ProcessEnvironmentBlock pointer from the TEB (GS segment offset 0x60). peb->Ldr reaches PEB_LDR_DATA, and ldr->InLoadOrderModuleList.Flink is the first loaded module.
  • Each FullDllName.Buffer is converted character-by-character from wide to a local CHAR ANSI[] array before hashing, so the resolver never needs WideCharToMultiByte.
  • The returned DllBase is cast to HMODULE. Lookups use the full DLL path string (e.g. C:\Windows\System32\ntdll.dll), which is why the module hash constants (ntdll = 776560387, kernelbase = 3314415166) reflect those full paths.
  • There is no bound on the walk; it iterates the load-order list until a hash match or the list cycles.

functions.h uses this at load time to grab hNT and hkb:

HMODULE hNT  = GetLoadedDllHandleH(776560387);   // ntdll
HMODULE hkb  = GetLoadedDllHandleH(3314415166);  // kernelbase

Bcrypt, by contrast, is loaded directly with LoadLibraryW(L"Bcrypt.dll") because that module is not guaranteed to be present in the load-order list yet.

Resolving a function address: GetFunctionAddressH (export-directory parsing)

GetFunctionAddressH(HMODULE DllHandle, DWORD dwHash) is the project's GetProcAddress replacement. It parses the module's PE headers and IMAGE_EXPORT_DIRECTORY, matching each export name against WEIRDHASHA(Name, 27).

uintptr_t DllBase = (uintptr_t)DllHandle;
PIMAGE_DOS_HEADER dos = (PIMAGE_DOS_HEADER)DllBase;      // check e_magic == IMAGE_DOS_SIGNATURE
PIMAGE_NT_HEADERS nt  = DllBase + dos->e_lfanew;         // check Signature == IMAGE_NT_SIGNATURE
PIMAGE_EXPORT_DIRECTORY pExport = DllBase + nt->OptionalHeader
                                        .DataDirectory[IMAGE_DIRECTORY_ENTRY_EXPORT].VirtualAddress;

PDWORD AddressOfNames      = DllBase + pExport->AddressOfNames;      // RVA list of name strings
PDWORD AddressOfFunctions  = DllBase + pExport->AddressOfFunctions;  // RVA list of entry points
PWORD  AddressOfOrdinals   = DllBase + pExport->AddressOfNameOrdinals;

for (int i = 0; i < pExport->NumberOfNames; i++) {
    char* Name = (char*)(DllBase + AddressOfNames[i]);
    if (dwHash == WEIRDHASHA(Name, 27))
        return (FARPROC)(DllBase + AddressOfFunctions[AddressOfOrdinals[i]]);
}
return NULL;

Steps:

  1. Validate the DOS and NT signatures; on mismatch it prints a diagnostic but continues.
  2. Compute the export directory RVA from the IMAGE_DIRECTORY_ENTRY_EXPORT data-directory entry and add the base to reach pExportDirectory.
  3. Resolve the three RVA tables (names, functions, name-ordinals) by adding DllBase to each stored RVA.
  4. Linear-scan AddressOfNames, hashing each ASCII export name with 27 iterations, and return the matching entry point resolved through the ordinal array.

Because the function name is what is hashed, the constants in functions.h such as GetFunctionAddressH(hNT, 3966201525) for NtWriteVirtualMemory are computed over the plain export name string ("NtWriteVirtualMemory"), not a decorated/import name. The e_-prefixed kernelbase/Bcrypt globals (e_ConvertThreadToFiber, e_BCryptDecrypt, ...) are resolved the same way, just on their respective module handles.

functions.h: the central registry

functions.h is where all resolved globals are materialized. Each line evaluates the resolver chains described above at static initialization and binds a typed pointer to GetFunctionAddressH (or GetSysCallByWalking):

  • Module handles — hNT, hkb via GetLoadedDllHandleH, hBcrypt via LoadLibraryW.
  • ntdll function pointers — NtWriteVirtualMemory, NtAllocateVirtualMemory, NtProtectVirtualMemory, NtReadVirtualMemory, RtlInitUnicodeString, RtlCreateProcessParametersEx, NtWaitForSingleObject, NtCreateEvent, each reinterpret_cast to the typedef declared in types.h.
  • kernelbase function pointers — the fiber APIs (e_ConvertThreadToFiber, e_CreateFiber, e_SwitchToFiber) and resource APIs (e_FindResourceW, e_LoadResource, e_LockResource, e_SizeofResource).
  • Bcrypt function pointers — the e_BCrypt* AES chain used by AES.h.
  • SSN / syscall variables — DWORD dwNt* (SSN values) and UINT_PTR sysCallNt* (decoy syscall addresses), populated by GetSysCallByWalking, which are extern "C" so syscalls.asm can reference them by plain symbol name.

SSN resolution & decoy syscall addresses: GetSysCallByWalking

For indirect syscalls, Ghost cannot just resolve a function pointer — it needs the service syscall number (SSN) that the syscall instruction reads from eax, plus the address of an unhooked syscall stub in ntdll to jump into. GetSysCallByWalking(dwFunctionHash, OUT PDWORD SSN, OUT UINT_PTR* SysCallAddr) computes both from the resolved function's surrounding ntdll code.

FARPROC pfunc = GetFunctionAddressH(GetLoadedDllHandleH(776560387), dwFunctionHash);
fAddress = (uintptr_t)pfunc;
int track = 1, offset = 0x20;
while (true) {
    PBYTE neighbor = (PBYTE)(fAddress + offset);
    if (!IsHooked(neighbor)) {                       // clean syscall stub found
        if (neighbor[5] != 0x00)                     // SSN is 3 bytes wide here
            *SSN = ((neighbor[5] << 8) | neighbor[4]) - track;
        else
            *SSN = (DWORD)neighbor[4] - track;
        *SysCallAddr = (uintptr_t)neighbor + 0x12;   // address of the syscall instruction
        return NULL;
    }
    track++; offset += 0x20;                         // hooked stub, move to next
}

The logic:

  1. Resolve the real ntdll function address by hash (GetFunctionAddressH on the hash-resolved ntdll base), as above.
  2. Scan forward through adjacent 0x20 (32-byte) function stubs. ntdll's exported syscall stubs are laid out contiguously at 0x20 stride, one per syscall, in SSN order.
  3. IsHooked(neighbor) checks the standard syscall prologue bytes 4C 8B D1 B8 (mov r10, rcx / mov eax, imm); if the prologue has been overwritten (a userland hook), it skips to the next stub and bumps track.
  4. From the first unhooked neighbor, the SSN is read out of the mov eax, <imm> immop (neighbor[4], or a 16-bit value at [4..5] when it is 3 bytes) and corrected by - track to account for the skipped hooked stubs.
  5. The decoy syscall address is set to neighbor + 0x12, the offset of the syscall instruction inside the clean stub.

functions.h invokes it for the four syscalls the assembly layer needs:

PVOID s = GetSysCallByWalking(2050401239, &dwNtCreateUserProccess, &sysCallNtCreateProcess); // NtCreateUserProcess
PVOID h = GetSysCallByWalking(809892425,  &dwNtReadVirtualMemory,  &sysCallNtRead);          // NtReadVirtualMemory
PVOID i = GetSysCallByWalking(3375077829, &dwNtProtectVirtualMemory,&sysCallNtProtect);       // NtProtectVirtualMemory
PVOID t = GetSysCallByWalking(2224556388, &dwNtTerminateProcess,   &sysCallNtTerminate);     // NtTerminateProcess

syscalls.asm then builds each Sys* thunk that loads the stored SSN into eax and jmps to the stored decoy address:

SysNtReadVirtualMemory:
    mov eax, dword [dwNtReadVirtualMemory]
    jmp qword [sysCallNtRead]
    ret

This keeps the syscall instruction executing from within ntdll (not from the caller's module that EDR scans), while the SSN value is supplied by the loader's own data. The full mechanism is covered on the indirect-syscalls page.

IsHooked: detecting a patched syscall prologue

IsHooked(PBYTE functionbytes) is the hook check GetSysCallByWalking relies on. It verifies the four bytes that begin a clean ntdll syscall stub match the standard epilog/prologue, and reports hooked if any byte differs:

BOOL IsHooked(PBYTE functionbytes) {
    if (functionbytes[0] != 0x4C && functionbytes[1] != 0x8b
        && functionbytes[2] != 0xd1 && functionbytes[3] != 0xb8)
        return TRUE; // hooked
    return FALSE;
}

The expected bytes 4C 8B D1 B8 are mov r10, rcx ; mov eax, <imm32>, the canonical opening of an ntdll syscall wrapper. A jmp hook or a software breakpoint transplanted into the prologue breaks this pattern, so the walker can skip tampered stubs and still land on a clean one. Because this only inspects the first four bytes, it is a heuristic — a sufficiently sophisticated hook that preserves the prologue would evade it — but it is sufficient for EDR trampoline hooks that overwrite the leading instructions.

Name-based variants used by unhooking

resolvers.h also carries two non-hashed variants for clarity in the unhooking path:

  • GetLoadedDllHandleByName(const wchar_t* DllName) — walks the same InLoadOrderModuleList, but matches BaseDllName with wcscmp. Passing NULL returns peb->ImageBaseAddress (the running EXE's base).
  • GetFunctionAddressByName(HMODULE, const char*) — the export-directory scan identical to GetFunctionAddressH, but matching export names with strcmp instead of WEIRDHASHA.

These are used where the code already knows the literal name (notably unhook.h), while the hashed variants hide string constants from the static import/string scan elsewhere.

Integration, invariants, and failure semantics

  • Everything resolves during static initialization. functions.h's globals are GetFunctionAddressH/GetSysCallByWalking calls evaluated before main(), so any module that includes functions.h can call the resolved pointers directly. There is no lazy/on-demand resolution.
  • Hash constants are coupled to the hash function and the build. A hardcoded DWORD is meaningless without WEIRDHASHA's exact seed, iteration counts (28 for modules, 27 for functions), and the * dwString + length folding. Changing the hash function invalidates every constant in functions.h. The page instruction on hash.h stresses this coupling deliberately.
  • The same module handle flows through both hash and name paths. GetImageSizeFromBase/ReadBufferFromProcess in unhook.h obtain ntdll via GetLoadedDllHandleH(776560387) and then use the name-based resolvers to read a clean copy, tying the hashed module base and the SSN machinery together.
  • Failure modes are non-fatal by design. GetFunctionAddressH returns NULL (no match found), GetLoadedDllHandleH loops indefinitely if the hash never matches (no explicit termination), and the signature/NT-mismatch checks print a diagnostic but continue. GetSysCallByWalking never explicitly returns the found syscall — its results are delivered through the out-parameters SSN and SysCallAddr.
  • SSN offset math depends on contiguous 0x20 stubs. The - track correction assumes hooked stubs are skipped in lockstep with the track counter, so the derived SSN always lands on the true service number even when leading stubs are patched.
  • Decoy address is always +0x12 inside the stub. The syscall instruction sits at that fixed offset within a 0x20 ntdll stub, so once an unhooked stub is identified both its SSN and its syscall address are known.

ETW Patching (etw.h)

Ghost disables Event Tracing for Windows (ETW) so that security products and the OS tracing primitive cannot observe its activity. It does this by editing the in-memory ntdll stubs of two system calls — NtTraceEvent and NtTraceControl — replacing the first instruction that actually performs the trace with an early ret (0xC3). The implementation lives entirely in etw.h, which exposes two functions: PatchETW() (the entry point) and ValidateMemory() (a helper that confirms a patch was written correctly).

etw.h is a concentrated example of the loader's core defensive idioms, so it ties together several other concepts:

  • API hashing (GetLoadedDllHandleH / GetFunctionAddressH from resolvers.h) locates ntdll and both trace functions without importing or naming them (see api-resolution-and-hashing).
  • Return-address spoofing (RetSpoofCall, Gdgt) wraps every call the patcher makes — NtProtectVirtualMemory, memcpy, and memcmp — so those calls' stack return addresses point at a call r12 ROP gadget instead of back into a scanning frame.
  • Error handling uses the NTAPI_VALIDATE_RETURN2VOID macro from defs.h for each NT API status check.

Callers invoke PatchETW() early in the loader's main, immediately after FlushNTDLL() and before any payload-decryption and injection work, so the tracing surface is disabled before suspicious operations begin (see loader-pipeline).

Why patch at offset +3

NtTraceEvent and NtTraceControl are x64 system-call stubs emitted by ntdll. Their prologue is the conventional 64-bit syscall prologue:

mov r10, rcx     ; 4C 8B D1  (3 bytes)
mov eax, <SSN>   ; B8 ?? ?? ?? ?? 
syscall

The first three bytes are the 3-byte mov r10, rcx, which Ghost must skip, because clobbering that instruction would break the stub's stack even after the ret. Patching the shift mov rcx argument would not neutralize ETW. Instead PatchETW writes 0xC3 (ret) at the byte at offset +3, i.e. immediately past mov r10, rcx, replacing the low byte of mov eax, <SSN>. On return to the stub the CPU now hits the inserted ret and bails out of the trace call before the syscall is issued, so no ETW notification event is emitted to the kernel.

unsigned char* ControlProtectionOffset = pNtTraceControl + 3;
unsigned char* EventProtectionOffset   = pNtTraceEvent + 3;
unsigned char sourceBuffer = 0xC3;   // ret

Both offsets are the same +3, reflecting that both exported trace stubs share the identical prologue shape.

Resolving the targets (API hashing)

Before touching memory, PatchETW finds its three dependencies using the loader's hash-based resolvers rather than GetModuleHandle/GetProcAddress or a hardcoded import.

HMODULE hNT = GetLoadedDllHandleH(776560387);                 // ntdll
unsigned char* pNtTraceEvent   = (unsigned char*)GetFunctionAddressH(hNT, 2226474731);
unsigned char* pNtTraceControl = (unsigned char*)GetFunctionAddressH(hNT, 2097340520);
  • GetLoadedDllHandleH(776560387) walks the PEB load-order list and returns the base of ntdll.dll.
  • GetFunctionAddressH(hNT, <hash>) parses ntdll's IMAGE_EXPORT_DIRECTORY and returns the export whose WEIRDHASHA matches. The constants 2226474731 (NtTraceEvent) and 2097340520 (NtTraceControl) are the two targets Ghost patches.

No string for either trace function ever appears in the binary; only the numeric hashes do.

Patching sequence

PatchETW performs a classic virtual-memory write pattern: change protection → write → verify → restore protection, applied once per target. The steps:

  1. Reserve the single-byte region ntsize = 1 at the +3 offset of each function.
  2. Make the byte writable+executable with NtProtectVirtualMemory(..., PAGE_EXECUTE_READWRITE, &oldProtect), checking the result with NTAPI_VALIDATE_RETURN2VOID.
  3. Write 0xC3 via memcpy.
  4. Verify the write with ValidateMemory (a memcmp), returning early with a fprintf error on mismatch.
  5. Restore the original protection with a second NtProtectVirtualMemory(..., oldProtect, &oldProtect), again validated.
NTSTATUS Controlstatus = (NTSTATUS)RetSpoofCall((void*)NtProtectVirtualMemory, 5, Gdgt,
    SELF_HANDLE, &ControlProtectionOffset, &ntsize,
    PAGE_EXECUTE_READWRITE, &dwOldProtectionControl);
NTAPI_VALIDATE_RETURN2VOID(NtProtectControl, Controlstatus);

RetSpoofCall(memcpy, 3, Gdgt, ControlProtectionOffset, &sourceBuffer, sizeof sourceBuffer);
if (ValidateMemory(ControlProtectionOffset, &sourceBuffer, sizeof(sourceBuffer)) != 0) {
    fprintf(stderr, "Error: failed to patch etw function NtTraceControl: Data mismatch after copy.\n");
    return;
}

SELF_HANDLE ((HANDLE)-1) targets the current process, as defined in defs.h.

ValidateMemory

ValidateMemory confirms that a write actually landed in the page before Ghost proceeds:

int ValidateMemory(const void * ptr1, const void * ptr2, size_t num){
    int result = reinterpret_cast<int>(RetSpoofCall(memcmp, 3, Gdgt, ptr1, ptr2, num));
    return result;
}

It is a thin ret-spoofed wrapper around memcmp(destination, sourceBuffer, 1). A nonzero return means the patched byte does not equal 0xC3, so PatchETW prints a mismatched-data error to stderr and aborts (returns) without proceeding to the second target. This guards against a patch that silently failed (for example, because the memory was not writable), rather than assuming the memcpy succeeded.

NTAPI_VALIDATE_RETURN2VOID error handling

Every NT API call in etw.h is checked with the NTAPI_VALIDATE_RETURN2VOID macro from defs.h:

#define NTAPI_VALIDATE_RETURN2VOID(API_NAME, STATUS) \
    if (STATUS != 0){ \
        std::cout << "{!!} " << #API_NAME << " failed with status: " \
                  << std::hex << STATUS << std::endl; \
        return; };

On a non-zero NTSTATUS it prints the failed API name and the hex status, then returns from the void function — exactly the behavior PatchETW (which returns void) needs. etw.h uses this specific macro (rather than the ..._RETURN / ..._RETURN2NULL siblings in defs.h) for all four protection-operation checks: NtProtectControl, NtProtectEvent, NtProtectControl2, and NtProtectEvent2 — the two "set to PAGE_EXECUTE_READWRITE" calls and the two "restore old protection" calls. Aborting on any failed protection change keeps Ghost from writing to a page or leaving it mis-protected when the syscall unexpectedly failed.

Invariants and failure semantics

  • The trace function is only patched if it was reachable: if hashing fails to resolve ntdll or either export, the pointers are NULL and the subsequent +3 arithmetic produces invalid addresses; PatchETW provides no explicit null-check before use, so a resolution failure manifests as a fault rather than a reported error.
  • Each write is verified before the second target is touched: a failed NtTraceControl patch stops the routine before NtTraceEvent is attempted.
  • Protection is restored to the original value, not left at PAGE_EXECUTE_READWRITE, so the memory remains as executable-as-before (and read-only) once patched, minimizing the modified-page footprint.
  • ETW is disabled before downstream work: Ghost.cpp calls FlushNTDLL() then PatchETW() before decrypting the payload, so the trace calls that would fire during later injection steps are neutralized first.

PatchETW owns no mutable state of its own; it is a one-shot, void operation with no cleanup requirement beyond restoring page protection, and it is only invoked once from main.

Fiber-Based Stack Hiding (hook.h)

Ghost hides the payload's (beacon's) entire call stack while it sleeps by combining a protected-memory trampoline hook over kernel32!Sleep with Windows Fibers. The hook redirects any beacon Sleep call to FiberSwitcher, which switches away to the loader's original fiber. Because fibers are userland-only execution units, neither the fiber switch nor the sleeping state triggers kernel callbacks, so an EDR observing thread/process activity sees the payload vanish rather than parked on a recognizable stack.

The mechanism lives in hook.h, which owns four pieces that work together:

  • HookFunction(PVOID FunctionToHook, PVOID RedirectionFunction) — installs the 13-byte trampoline that redirects a target (here Sleep) to our handler.
  • FiberSwitcher(DWORD dwMilliseconds, ...) — the extern "C" hook handler; records the sleep duration and switches back to InitialFiber.
  • dwSleepTime — a module-global DWORD that bridges the hook to the waiting loop by carrying the requested sleep duration in milliseconds.
  • DelayExecution(DWORD dwMilliseconds) — the actual sleep, done with an event + wait so the loader thread blocks without any beacon frame on the stack.

The fiber infrastructure itself is set up in Ghost.cpp (see loader-pipeline): main() converts the current thread to InitialFiber with ConvertThreadToFiber, then creates the payload fiber Creation from the decrypted, executable shellcode with CreateFiber. From there, main() loops: switch to the payload fiber → it runs until it calls Sleep → the hook fires → switch back → DelayExecution → repeat.

The trampoline hook (HookFunction)

HookFunction installs a minimal, hardcoded x64 trampoline over the target function's prologue. The author's own comment on the dialog is blunt: "its shit, BUT it works" — it overwrites the first 13 bytes of the target without preserving or relocating the original prologue, so it is only safe when the target is a function whose overwritten bytes are never needed again (a Sleep stub the beacon uses purely to pause).

uint8_t uHook[] = {
    0x49, 0xBA, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00, 0x00,  // 49 BA imm64  -> mov r10, <imm64>
    0x41, 0xFF, 0xE2                                             // 41 FF E2     -> jmp r10
};

The first ten bytes are mov r10, imm64 (opcode 49 BA followed by an 8-byte immediate), and the final three bytes are jmp r10 (41 FF E2). The immediate is filled in at runtime with the address of RedirectionFunction (the hook handler), so executing the first byte of Sleep loads the handler's address into r10 and jumps straight to it. This is a fixed-length, position-independent prologue patch — no relative jump math, no need to know the target address at compile time.

The patch sequence wraps every operation in the loader's ret-spoofing wrapper:

  1. Write the target address into the stub. RetSpoofCall((void*)memcpy, 2, Gdgt, &uHook[2], &uPatch, sizeof(uPatch)) copies the 8-byte RedirectionFunction pointer into uHook bytes 2–9 (the imm64 slot).
  2. Make the target writable. RetSpoofCall(NtProtectVirtualMemory, 5, Gdgt, SELF_HANDLE, &baseAddress, &regionSize, PAGE_READWRITE, &oldProtect) flips the page containing FunctionToHook to PAGE_READWRITE, validated with NTAPI_VALIDATE_RETURN2VOID(NtProtectHook1, status).
  3. Copy the 13-byte stub over the target. RetSpoofCall((void*)memcpy, 3, Gdgt, FunctionToHook, uHook, sizeof(uHook)).
  4. Restore the original protection. A second NtProtectVirtualMemory(..., oldProtect, &oldProtect) returns the page to its prior state, again validated (NtProtectHook2).

All of these are routed through RetSpoofCall so the hook-installation calls themselves do not leave a detectable inline return address (see return-address-spoofing). Because the stub only jumps and never preserves the original bytes, a stack unwinder that reads the patch as ordinary code simply sees the jump; the trampoline is not designed to be callable or to return to the original Sleep.

FiberSwitcher: the extern "C" hook handler

FiberSwitcher is the function Sleep now jumps to. It is deliberately declared extern "C" so its name has C linkage (no C++ mangling) and it can be passed by address into the assembly/ret-spoofing machinery without decoration issues:

extern "C" void FiberSwitcher(DWORD dwMilliseconds, ...) {
    dwSleepTime = dwMilliseconds;
    RetSpoofCall((void*)e_SwitchToFiber, 1, Gdgt, InitialFiber);
    return;
}

Its job is only two things:

  1. Record the requested duration into the global dwSleepTime so the loader thread can later reproduce the actual sleep. FiberSwitcher itself never sleeps — it just stashes the value.
  2. Switch back to InitialFiber via RetSpoofCall((void*)e_SwitchToFiber, 1, Gdgt, InitialFiber). The source comment marks precisely what this achieves: "when this is executed by the beacon the entire beacon stack gets hidden for the time it sleeps."

FiberSwitcher takes (DWORD dwMilliseconds, ...) — the variadic ellipsis absorbs Sleep's unused second argument (dwMilliseconds only on SleepEx), keeping the call-compat convention flexible for whichever sleep API is hooked. When SwitchToFiber eventually returns (after the loader thread completes its delay and switches back), FiberSwitcher simply returns, which resumes the beacon's Sleep call as if it normally completed.

dwSleepTime: the global bridge

dwSleepTime is a plain module-scope DWORD declared in hook.h (no extern in the header, so it is a single translation-unit global shared by hook.h's functions within the same compilation unit that includes it). It is the connective tissue between the two halves of the sleep mechanism:

  • Producer: FiberSwitcher writes dwSleepTime = dwMilliseconds when a beacon Sleep is intercepted.
  • Consumer: main()'s loop reads DelayExecution(dwSleepTime) after SwitchToFiber returns control, i.e. after the hook fired.

Because the payload fiber and the loader thread run on the same OS thread (fibers multiplex on one thread), and because FiberSwitcher runs on the payload fiber just before switching away, the write to dwSleepTime is always visible to main() before it schedules the delay — there is no cross-thread synchronization required.

DelayExecution: sleeping without a visible stack

DelayExecution performs the real pause using the NT event/wait pair instead of Sleep, so that while the loader thread blocks, the only thing on the stack is the loader's own frames (and the ret-spoofed call chain), not the beacon's.

extern "C" void DelayExecution(DWORD dwMilliseconds) {
    LARGE_INTEGER DelayInterval = { 0 };
    LONGLONG Delay = NULL;
    HANDLE hEvent = NULL;

    RetSpoofCall(NtCreateEvent, 5, Gdgt, &hEvent, EVENT_ALL_ACCESS, NULL, 0, FALSE);
    Delay = dwMilliseconds * 10000;
    DelayInterval.QuadPart = -Delay;
    RetSpoofCall(NtWaitForSingleObject, 3, Gdgt, hEvent, FALSE, &DelayInterval);
    return;
}
  • NtCreateEvent(..., FALSE) creates an event with EVENT_ALL_ACCESS, no object attributes, and initial state FALSE (non-signaled).
  • The requested milliseconds are converted to a relative timeout in 100 ns units (dwMilliseconds * 10000) and negated so NtWaitForSingleObject treats it as a relative interval rather than an absolute time.
  • NtWaitForSingleObject(hEvent, FALSE, &DelayInterval) blocks the thread for that interval. Since the event is never signaled by anyone, the wait expires on its own after the timeout — a pure timed block with no signaled-object dependency.

Both calls are ret-spoofed, and neither emits the kind of call that would disclose the beacon's context. From the loader thread's perspective, the loop simply: switch to payload → payload calls Sleep → hook switches back → DelayExecution(dwSleepTime) blocks for the requested interval → loop again.

Why fibers hide the stack from kernel callbacks

Windows Fibers are a userland-only scheduling primitive: ConvertThreadToFiber, CreateFiber, and SwitchToFiber run entirely in the process context with no kernel scheduling decision and therefore no kernel callback (unlike thread creation/suspension, which EDRs observe via PsSetCreateThreadNotifyRoutine and related callbacks). The repository README states this directly:

ghost makes use of Fiber threads to circumvent this detection technique, fiber threads are userland only execution units that does not alert any registered kernel callbacks

The consequence for stack hiding: when the beacon calls Sleep and FiberSwitcher switches to the loader's InitialFiber, the beacon's stack frames are swapped out of the live thread stack entirely. Any EDR that walks the current thread's stack at that moment sees only the loader's frames (main, DelayExecution, the ret-spoofed NT calls) — the beacon's call frames are nowhere on the current stack. When the delay ends and the loop switches back to the payload fiber, the beacon's frames are restored in full. This is the second of Ghost's two stack-hiding techniques (the first being per-call return-address spoofing via RetSpoofCall).

sequenceDiagram participant M as MainInitialFiber participant P as PayloadFiber participant H as SleepHook participant D as DelayExecution M->>M: ConvertThreadToFiber (InitialFiber) M->>M: CreateFiber(payload entry) = Creation loop while true M->>P: SwitchToFiber(Creation) Note over P: payload/beacon runs P->>H: calls Sleep(dwMilliseconds) H->>H: dwSleepTime = dwMilliseconds H->>M: SwitchToFiber(InitialFiber) Note over M: beacon stack hidden M->>D: DelayExecution(dwSleepTime) Note over D: NtCreateEvent + NtWaitForSingleObject (event wait) D-->>M: timeout expires, returns end

The fiber switching sleep cycle: main converts itself to a fiber, creates the payload fiber from executable shellcode, then alternates — switch to payload → it calls Sleep → the hooked FiberSwitcher switches back → main DelayExecution's → loop.

C2-assumption: hooking Sleep assumes Cobalt Strike

The whole scheme pivots on the beacon actually pausing via kernel32!Sleep (or SleepEx). HookFunction(Sleep, FiberSwitcher) in Ghost.cpp hardcodes the symbol Sleep, which is correct for a Cobalt Strike-style beacon. The README is explicit that this assumption is a customization point:

Ghost heavily relies on understanding how your beacon sleeps, in case of cobalt strike the kernel32!Sleep function is hooked and replaced with fiber calls to allow switching and hiding the beacon callstack. If you want to use it with other C2 beacons you will need to use a tool like apimonitor to intercept api calls for your "beacon", detect the api called on sleep and replacing it in Ghost.cpp to hook it, for example for MDSec's NightHawk one of the CreateThreadPool APIs needs to be hooked.

So for other C2s the pipeline is identical — same HookFunction trampoline, same FiberSwitcher/DelayExecution pair, same loop — but the first argument to HookFunction must be swapped for the sleep API that beacon actually calls. This is why FiberSwitcher keeps the variadic ...: its signature is tolerant of the differing auxiliary arguments different sleep APIs pass.

State, lifecycle, and invariants

  • Setup (main(), Ghost.cpp): HookFunction(Sleep, FiberSwitcher) runs before any fiber is created, so Sleep is already redirected when the payload fiber first runs. Then InitialFiber = ConvertThreadToFiber(NULL) converts the current loader thread, and Creation = CreateFiber(NULL, pLPI->lpData, NULL) creates the payload fiber whose start routine is the decrypted shellcode.
  • Steady state: main()'s infinite while (true) loop is the sole scheduler: SwitchToFiber(Creation) runs the beacon until it calls Sleep; the hook then SwitchToFiber(InitialFiber) back; DelayExecution(dwSleepTime) blocks; and the loop resumes. The beacon never yields control except through the hooked Sleep.
  • Lifecycle invariant — single-threaded fiber multiplexing: all switches happen on one OS thread, so there is no data race on dwSleepTime: the hook writes it on the payload fiber immediately before the switch back, and main() reads it only after the switch has returned.
  • No return from main(): the loop is unbounded; main() never reaches its return 0 because SwitchToFiber/DelayExecution always loop back.

Failure semantics and limitations

  • HookFunction never preserves the original prologue. Overwritten bytes of Sleep are gone; the trampoline is a one-way jump. If the target function were ever genuinely needed (not merely to block), this hook would break it — the author's own "it's shit, BUT it works" caveat.
  • Protection failures abort the hook. Each NtProtectVirtualMemory result is validated with NTAPI_VALIDATE_RETURN2VOID; on nonzero NTSTATUS the function returns without installing the hook, and the loader continues (the hook simply never takes effect).
  • Broken if the beacon sleeps through a different API. If the beacon does not call the hooked symbol, the fiber loop's SwitchToFiber(Creation) returns only when the beacon itself switches/returns, and the Sleep-driven timing never engages. This is the central limitation the README flags and why the hook target must match the C2's sleep call.

Indirect Syscalls & SSN Resolution (syscalls.asm)

Ghost performs its most sensitive native calls — process creation, virtual-memory read/protect, and process termination — through indirect syscalls: small assembly thunks in syscalls.asm load a service syscall number (SSN) from a global variable and then jmp to a decoy syscall instruction that lives inside ntdll itself. This page documents the four assembly stubs, how they are wired to the C++ globals in functions.h, where they are used, and why executing the syscall instruction at a decoy address defeats EDR hooks that patch stub code.

The mechanism has three cooperating layers:

  • syscalls.asm — NASM code (assembled with nasm -f win64 into syscalls.o) that defines the SysNt* thunks. It is NOT MASM: the file header warns it "can only be assembled with NASM assembler".
  • functions.h — declares the extern "C" SSN/decoy-address globals and populates them at static initialization by calling GetSysCallByWalking from resolvers.h.
  • resolvers.h — GetSysCallByWalking walks ntdll's contiguous 0x20-byte syscall stubs to derive each SSN and a decoy syscall address (see api-resolution-and-hashing).

The four assembly stubs (syscalls.asm)

Each exported thunk follows the same shape. SysNtCreateUserProcess opens with a lea and the other three use mov, but all four do the same three things:

  1. Move the first register argument rcx into r10 — the x64 fastcall/windows syscall convention requires the syscall number in eax and the first argument in r10 (the syscall instruction clobbers rcx).
  2. Load the SSN from a global DWORD variable into eax.
  3. jmp qword [sysCallXxx] — an indirect jump to the stored decoy syscall address.
; NtReadVirtualMemory stub
global SysNtReadVirtualMemory
SysNtReadVirtualMemory:
    mov r10, rcx
    mov eax, dword [dwNtReadVirtualMemory]
    jmp qword [sysCallNtRead]
    ret

The ret after the jmp is never reached in normal flow — it is a leftover guard so the function ends cleanly if the jmp is ever bypassed or patched. The four stubs and their SSN globals / decoy-address globals are:

Stub (exported) SSN global Decoy global
SysNtCreateUserProcess dwNtCreateUserProccess sysCallNtCreateProcess
SysNtReadVirtualMemory dwNtReadVirtualMemory sysCallNtRead
SysNtProtectVirtualMemory dwNtProtectVirtualMemory sysCallNtProtect
SysNtTerminateProcess dwNtTerminateProcess sysCallNtTerminate

Note the typo dwNtCreateUserProccess (double "c") is preserved in both the assembly extern and the C++ definition — they must match exactly for the linker to resolve the symbol.

extern wiring between syscalls.asm and functions.h

syscalls.asm declares the two families of globals it consumes as extern:

extern dwNtCreateUserProccess
extern dwNtReadVirtualMemory
extern dwNtProtectVirtualMemory
extern dwNtTerminateProcess

extern sysCallNtCreateProcess
extern sysCallNtRead
extern sysCallNtProtect
extern sysCallNtTerminate

functions.h defines those same symbols inside an extern "C" block so C++ name mangling does not break the link with the NASM object:

extern "C" {
    // SSN Variables
    DWORD dwNtCreateUserProccess = 0;
    DWORD dwNtReadVirtualMemory = 0;
    DWORD dwNtProtectVirtualMemory = 0;
    DWORD dwNtTerminateProcess = 0;

    // SYSCALL Variables
    UINT_PTR sysCallNtCreateProcess = 0;
    UINT_PTR sysCallNtRead = 0;
    UINT_PTR sysCallNtProtect = 0;
    UINT_PTR sysCallNtTerminate = 0;
}

The extern declarations in the assembly reference the C++ DWORD (4-byte SSN) and UINT_PTR (8-byte decoy-address) definitions by plain symbol name. build.py assembles syscalls.asm with NASM (NASM -f win64 syscalls.asm -o build/syscalls.o) and links that object together with the C++ translation unit, at which point the linker resolves the assembly externs against the functions.h definitions.

Resolving the SSN and decoy address: GetSysCallByWalking

The SSN and decoy-address globals are not hardcoded. At static initialization, functions.h drives GetSysCallByWalking once per syscall, supplying an output pointer for both the SSN and the decoy address:

PVOID s = GetSysCallByWalking(2050401239, &dwNtCreateUserProccess, &sysCallNtCreateProcess); // NtCreateUserProcess
PVOID h = GetSysCallByWalking(809892425,  &dwNtReadVirtualMemory,  &sysCallNtRead);          // NtReadVirtualMemory
PVOID i = GetSysCallByWalking(3375077829, &dwNtProtectVirtualMemory,&sysCallNtProtect);       // NtProtectVirtualMemory
PVOID t = GetSysCallByWalking(2224556388, &dwNtTerminateProcess,   &sysCallNtTerminate);     // NtTerminateProcess

GetSysCallByWalking (in resolvers.h) resolves the real exported ntdll function by hash, then walks the adjacent 0x20-byte syscall stubs that ntdll lays out contiguously in SSN order. For the first neighbor considered clean by IsHooked (standard prologue 4C 8B D1 B8 = mov r10, rcx / mov eax, imm), it:

  • reads the SSN from the stub's mov eax, imm operand (neighbor[4], or a 16-bit value when a 3-byte SSN is present), corrected by - track to account for skipped hooked stubs, and writes it into the dwNt* global; and
  • writes neighbor + 0x12 — the offset of the syscall instruction inside the clean stub — into the sysCallNt* global.

So after static initialization, dwNtX holds the numeric SSN and sysCallNtX holds the address of an unhooked syscall instruction inside ntdll. The full algorithm is documented on api-resolution-and-hashing.

Where the stubs are used

The four SysNt* thunks are never called directly; they are always funneled through RetSpoofCall so return-address spoofing rides on top of the indirect syscall.

unhook.h performs ntdll unhooking by first spawning a suspended audiodg.exe, reading a clean copy of ntdll from it, and then restore-writing that copy over the local .text section. All three native operations use the syscall stubs:

  • SysNtReadVirtualMemory — ReadBufferFromProcess reads the remote, clean ntdll image (RetSpoofCall(SysNtReadVirtualMemory, 5, Gdgt, hProcess, BASE, bufferMemory, ...)).
  • SysNtTerminateProcess — ReadBufferFromProcess tears down the temporary process after the read (RetSpoofCall((void*)SysNtTerminateProcess, 2, Gdgt, hProcess, 0)).
  • SysNtProtectVirtualMemory — FlushNTDLL flips the local .text section to PAGE_EXECUTE_WRITECOPY, copies the clean bytes, then restores the original protection (two RetSpoofCall(SysNtProtectVirtualMemory, 5, Gdgt, SELF_HANDLE, ...) calls).

ntprocessapi.h builds a suspended process via NtCreateUserProcess: NtCreateUserSuspendedProcess composes an UNICODE_STRING, process parameters, and a PS_ATTRIBUTE_LIST with PS_ATTRIBUTE_IMAGE_NAME, then invokes SysNtCreateUserProcess through RetSpoofCall with 11 arguments (including THREAD_CREATE_FLAGS_CREATE_SUSPENDED) to get back a suspended process and thread handle.

The caller passes argument counts to RetSpoofCall (5 for read/protect, 2 for terminate, 11 for create-user-process) so the variadic spoofing prologue shifts the remaining stack arguments correctly before jumping into the Sys* thunk.

Why this is "indirect" and what it defeats

A direct syscall call would place the syscall instruction inside the caller's own module, at the end of a custom stub. EDRs that hook ntdll scan for this pattern — a syscall instruction executing from an unexpected (non-ntdll) address is a strong detection signal, and EDRs also patch the first bytes of ntdll's exported stubs with a jmp to an instrumentation routine.

The Ghost stubs are indirect because the Sys* thunk in the caller's module never executes the syscall instruction. Instead it loads the SSN and jmps to a decoy syscall address that GetSysCallByWalking located inside ntdll, in a clean (unhooked) stub. The control flow is:

sequenceDiagram
    participant App as Caller module
    participant Thunk as SysNt* thunk (syscalls.asm)
    participant Ntdll as ntdll decoy stub
    participant Kernel as Windows kernel
    App->>Thunk: RetSpoofCall(SysNt*, nArgs, Gdgt, args)
    Thunk->>Thunk: mov r10, rcx ; mov eax, [dwNtX]
    Thunk->>Ntdll: jmp [sysCallNtX]  (decoy syscall addr)
    Ntdll->>Kernel: syscall (SSN in eax, args in r10)
    Kernel-->>Ntdll: NTSTATUS return
    Ntdll-->>App: ret via spoofed return address

Execution of the syscall instruction happens at the decoy address inside ntdll, not in the caller's stub, so EDR hooks that overwrite stub code are never executed.

By jumping into a clean ntdll stub, the syscall instruction executes from a legitimate ntdll address (thwarting the "syscall from non-ntdll" heuristic), while the SSN is supplied from the loader's own dwNt* data — so the loader does not depend on the potentially hooked export stub, only on the clean syscall endpoint it found by walking. EDR hooks that overwrite the leading bytes of an ntdll stub (the mov r10, rcx / mov eax, imm prologue) or that patch stub code are bypassed because those bytes are in the caller's thunk, not in the executed path; and if GetSysCallByWalking reaches a hooked neighbor it simply walks past it to the next clean stub.

Invariants and failure semantics

  • The SSN and decoy address must both be resolved before any Sys* call. GetSysCallByWalking is evaluated during static initialization of functions.h, so by the time main() runs (via FlushNTDLL in Ghost.cpp) every dwNt* and sysCallNt* global holds a valid value. The globals default to 0, so calling a thunk before resolution would jump to address 0; in practice they are always resolved first.
  • The decoy address points inside ntdll and lands on the syscall instruction (+0x12). GetSysCallByWalking computes it from a clean neighbor stub, so the jmp transfers control into an ntdll syscall epilogue, not into a hook trampoline. If the running build's stub layout differs (a non-0x20 stride or a different syscall offset), the +0x12 constant and the - track SSN correction would need to change.
  • The two symbol families must match exactly across assembly and C++. The NASM externs are resolved against the extern "C" DWORD/UINT_PTR definitions in functions.h; any rename (including the existing dwNtCreateUserProccess typo) must be mirrored on both sides or the link fails.
  • Assembly is NASM-only. build.py assembles syscalls.asm with NASM into win64 object format; MASM/other assemblers cannot consume the DEFAULT REL / [BITS 64] source.
  • ret after jmp is dead code. Each stub ends with ret, but the preceding one-way jmp makes it unreachable during a successful call; it exists so the function has a defined end rather than falling through.

NTDLL Unhooking via Suspended Process (unhook.h, ntprocessapi.h)

Ghost evicts EDR hooks planted in the local ntdll.dll copy by extracting a pristine ntdll image from a freshly created, suspended audiodg.exe process and overwriting the local .text section with it. The entire procedure lives in unhook.h (orchestration and memory rewriting) and ntprocessapi.h (suspended-process creation), and every sensitive native operation is executed through indirect syscalls wrapped in RetSpoofCall so the loader never calls hookable export stubs.

This page documents the entry point FlushNTDLL(), the two helpers GetImageSizeFromBase() and ReadBufferFromProcess(), the NtCreateUserSuspendedProcess wrapper, and the important invariants that make the unhook reliable.

Entry point: FlushNTDLL()

FlushNTDLL() in unhook.h is the very first statement of main() in Ghost.cpp:

int main() {
    FlushNTDLL();
    PatchETW();
    // ...
}

It runs before anything else — before ETW patching, before resource loading and decryption, before fiber setup — so that by the time the payload executes, userland ntdll hooks hosted by an EDR are gone. Its return type is VOID: on failure it prints an error and returns, but does not halt the loader (experienced as a degraded, still-hooked ntdll rather than a crash). The pipeline order and the reason it is first are documented on loader-pipeline.

Unhooking steps

FlushNTDLL() composes the following sequence:

  1. Read the clean image — call ReadBufferFromProcess(&clean_buffer) to obtain a heap buffer holding a pristine ntdll image read from a suspended audiodg.exe.
  2. Resolve the local ntdll base — via GetLoadedDllHandleH(776560387) (PEB load-order walk, hash 776560387 is C:\Windows\System32\ntdll.dll; see api-resolution-and-hashing). The DOS and NT headers are validated with IMAGE_DOS_SIGNATURE / IMAGE_NT_SIGNATURE; a mismatch prints IMAGE_DOS_SIGNATURE MISMATCH / IMAGE_NT_SIGNATURE MISMATCH and aborts the function.
  3. Find the .text section — iterate pntheaders->FileHeader.NumberOfSections using IMAGE_FIRST_SECTION, and when strcmp(SECTIONS_ENTRY[i].Name, ".text") == 0, record:
    • LOCAL_SECTION = base + VirtualAddress (the target in our process),
    • REMOTE_SECTION = clean_buffer + VirtualAddress (the clean source),
    • SECTION_SIZE = Misc.VirtualSize.
  4. Make local section writable — SysNtProtectVirtualMemory (indirect syscall through RetSpoofCall, 5 args, SELF_HANDLE = (HANDLE)-1) flips the local .text to PAGE_EXECUTE_WRITECOPY, saving the old protection in old_protect. Failure prints Protection 1 Error and returns.
  5. Copy the clean bytes — RetSpoofCall((void*)memcpy, 3, Gdgt, LOCAL_SECTION, REMOTE_SECTION, SECTION_SIZE) overwrites the hooked local .text with the clean remote bytes.
  6. Restore protection — a second SysNtProtectVirtualMemory restores old_protect, then the clean buffer is freed with delete[] clean_buffer.

The two NtProtectVirtualMemory calls plus memcpy and the remote read are all ret-spoofed (the ROP gadget Gdgt is the shared return address), so the unhook itself does not leave a spoofable stack trace for EDR unwinding (see indirect-syscalls).

sequenceDiagram participant M as main() / FlushNTDLL participant NP as NtCreateUserSuspendedProcess participant R as SysNtReadVirtualMemory participant P as NtProtectVirtualMemory M->>NP: create suspended audiodg.exe (SysNtCreateUserProcess) NP-->>M: hProcess, hThread M->>R: remote read of clean ntdll into buffer R-->>M: clean ntdll image buffer M->>M: find local .text section (base + VirtualAddress) M->>P: NtProtectVirtualMemory -> PAGE_EXECUTE_WRITECOPY P-->>M: old protection saved M->>M: memcpy clean .text over local .text M->>P: NtProtectVirtualMemory -> restore old protection

End-to-end unhook: a suspended audiodg.exe is created, its pristine ntdll is read remotely, and the local .text section is temporarily made writable, overwritten, and re-protected.

Helper: GetImageSizeFromBase()

GetImageSizeFromBase() (unhook.h) resolves the module size of the loaded ntdll:

  • Gets the ntdll handle via GetLoadedDllHandleH(776560387) and casts it to a uintptr_t base.
  • Validates IMAGE_DOS_SIGNATURE and IMAGE_NT_SIGNATURE (DOS MISMATCH / NT MISMATCH on failure, returning NULL).
  • Returns pntheaders->OptionalHeader.SizeOfImage, i.e. the full in-memory size of ntdll.

This SizeOfImage is the byte count ReadBufferFromProcess allocates and reads from the remote process, guaranteeing the buffer is large enough to hold the entire clean ntdll image.

Helper: ReadBufferFromProcess()

ReadBufferFromProcess(OUT PBYTE* BUFFER) (unhook.h) performs the remote acquisition:

  1. sizeofheap = GetImageSizeFromBase() and BASE = GetLoadedDllHandleH(776560387) — the image size and the local base.
  2. NtCreateUserSuspendedProcess(L"\\??\\C:\\Windows\\System32\\audiodg.exe", &hProcess, &hThread) spawns a suspended process. The \\??\\ prefix is the NT namespace path for the device-absolute audiodg.exe. A non-success status or a null/invalid handle prints Process Creation Error (but the function continues).
  3. bufferMemory = malloc(sizeofheap), zeroed with RtlSecureZeroMemory.
  4. status = RetSpoofCall(SysNtReadVirtualMemory, 5, Gdgt, hProcess, BASE, bufferMemory, sizeofheap, &lpNumberOfBytesRead) — reads sizeofheap bytes of ntdll from the remote suspended process's address space starting at its ntdll base. Failure prints Read Error.
  5. RetSpoofCall((void*)SysNtTerminateProcess, 2, Gdgt, hProcess, 0) tears down the temporary process (terminating with exit code 0). Failure prints Termination Error.
  6. *BUFFER = bufferMemory returns the allocated clean image to the caller.

Because audiodg.exe is spawned suspended, its ntdll is mapped but its loader and any EDR userland instrumentation that would run at process start have not initialized — so its ntdll .text is the pristine on-disk bytes, free of hooks.

NtCreateUserSuspendedProcess (ntprocessapi.h)

NtCreateUserSuspendedProcess(const wchar_t* szProcessName, PHANDLE hCreatedProcess, PHANDLE hCreatedThread) (ntprocessapi.h) wraps NtCreateUserProcess through the SysNtCreateUserProcess indirect syscall.     • Size = NtImagePath.Length,

Hardcoded target and why audiodg.exe

unhook.h and ntprocessapi.h hardcode the single target image \??\C:\Windows\System32\audiodg.exe (Windows Audio Device Graph Isolation). audiodg.exe is a signed system binary that ships with Windows, executes from a trusted path, and by default has ntdll mapped without early userland hook instrumentation active in a suspended process. Using a suspended process sidesteps the need to read ntdll from disk (which can itself be tampered or re-parsed on disk) and avoids resolving a clean module handle inside the already-hooked local process.

Invariants and failure semantics

  • FlushNTDLL() must run before any hooked API is relied upon. It is the first statement of main(). Until it completes, direct calls to functions like GetProcAddress-style resolvers are fine (they walk the PEB / parse exports), but any EDR-hooked syscall export would redirect to the hook.
  • The local and remote images are assumed to be the same build. The remote buffer is read at the local base and the same section RVAs are used for both; if the OS provides a patched/updated ntdll to the new process that differs from the loaded one, the overwrite could introduce a version-skew into the local .text. The code makes no version check.
  • Signature validation gates the whole flow. Both GetImageSizeFromBase() and FlushNTDLL() check IMAGE_DOS_SIGNATURE / IMAGE_NT_SIGNATURE and print a mismatch rather than dereferencing an invalid header. FlushNTDLL() returns (VOID) on mismatch, leaving ntdll hooked.
  • Errors are non-fatal by design. VOID returns and std::cout diagnostics mean each step reports and continues rather than aborting the process. This is consistent with _DEBUG_PRINT-gated logging in the loader.
  • Protection must be restored even on the copy path. If the first NtProtectVirtualMemory fails, FlushNTDLL() returns before modifying any bytes, so .text is never left writable-execute non-copied. The second protect restores old_protect (the exact prior protection, not a hardcoded constant).
  • Memory management: ReadBufferFromProcess hands ownership of the malloc'd buffer to the caller; FlushNTDLL frees it with delete[] clean_buffer after the copy.
  • Temporary process lifecycle: ReadBufferFromProcess terminates the spawned audiodg.exe immediately after the read, so no orphan window is left running.

Return Address Spoofing (RetSpoofCall)

Ghost routes nearly every sensitive call through a single variadic assembly wrapper, RetSpoofCall in retaddrspoof.asm, whose purpose is to hide the loader's own call stack from EDR stack unwinding. Instead of returning into a frame in the loader's module, the wrapped function returns through a randomly chosen ROP gadget — a call r12 instruction (41 FF D4) located inside ntdll — so an unwinder walking the stack sees the caller as a legitimate ntdll gadget rather than a loader frame. This is the per-call stack-hiding technique that every other module composes with (see loader-pipeline, etw-patching, ntdll-unhooking, and indirect-syscalls).

The primitive has two cooperating halves:

  • retaddrspoof.h — declares RetSpoofCall as an extern "C" variadic function and implements FindROPGadget, which locates the call r12 gadget inside ntdll's executable sections.
  • retaddrspoof.asm — the NASM implementation of RetSpoofCall that marshals the target function's variadic arguments, plants the gadget as the return address, jumps into the target, and later fixes up the frame.

The calling-convention shift

RetSpoofCall changes the normal Win64 convention by consuming the first three register arguments itself and passing the rest through to the real target:

extern "C" void* RetSpoofCall(void* Function, unsigned long long nArgs, void* r12_gadget, void* argN, ...);
  • rcx — Function — the address of the function to invoke (an API, an NT function, or a SysNt* indirect-syscall thunk).
  • rdx — nArgs — the number of real arguments to pass to Function (excluding the three wrapper arguments).
  • r8 — r12_gadget — the ROP gadget (the call r12 address from Gdgt) that becomes the target's return address.
  • r9 onward / stack — argN... — the target function's actual arguments, shifted down three slots.

Because the prologue shifts everything down by three, the same variadic wrapper works for any target arity. The header documents the return value as void* so a result (an NTSTATUS, a handle, a pointer) can be cast to whatever the caller expects.

Typical call sites pass the resolved function pointer first and the global gadget third, e.g. from Ghost.cpp:

status = reinterpret_cast<NTSTATUS>(RetSpoofCall((void*)NtProtectVirtualMemory, 5, Gdgt, SELF_HANDLE, &pLPI->lpPage, &pLPI->uSize, PAGE_EXECUTE_READ, &OldAccessProtection));

Finding the gadget: FindROPGadget

FindROPGadget in retaddrspoof.h locates a valid call r12 gadget inside ntdll to use as the planted return address:

  1. It reads the ntdll base from the hNT global (the hash-resolved HMODULE in functions.h) and validates the DOS signature (e_magic == IMAGE_DOS_SIGNATURE) and NT signature (Signature == IMAGE_NT_SIGNATURE).
  2. It walks every section header and keeps only sections with both IMAGE_SCN_CNT_CODE and IMAGE_SCN_MEM_EXECUTE (i.e. executable code sections, so the returned address is executable).
  3. Within each such section it scans every byte for the 3-byte pattern 41 FF D4, checked by IsValidGadgetx64 (*pbAddress == 0x41 && *(pbAddress+1) == 0xFF && *(pbAddress+2) == 0xD4), which is the call r12 instruction.
  4. Valid matches are collected into a local lpGadgets[MAX_GADGETS] array (zeroed with RtlSecureZeroMemory), capped at MAX_GADGETS (30); the scan stops early once 30 are found.
  5. It returns (PBYTE)lpGadgets[GEN_RAND(0, dwGadgetCount)], i.e. one randomly chosen instance, so the spoofing return address differs run to run. GEN_RAND(min, max) is rand() % (max + 1 - min) + min.

The gadget must be a call r12 (not just any call) because the assembly prologue loads the real return handler into r12 — the gadget's call r12 jumps to Fixup, which restores the loader's stack frame before control returns to the original caller.

The global Gdgt

The randomly chosen gadget is stored once in the global PVOID Gdgt:

PVOID Gdgt = FindROPGadget(); // used all across the project for ret address spoofing

This is defined in Ghost.cpp at static-initialization time (before main() runs) and extern'd across the modules that spoof their calls — allocator.h, unhook.h, etw.h, AES.h, hook.h, rsrc.h, and ntprocessapi.h all declare extern PVOID Gdgt; and pass it as the third argument to RetSpoofCall. Because it is resolved once up front, every module reuses the same gadget for the lifetime of the process. This is why the gadget is also available at exactly the point where the wrapper's lea r12, Fixup and the gadget's call r12 agree on what r12 means.

How RetSpoofCall works (assembly)

retaddrspoof.asm is NASM-only — its header states NOT MASM, it uses [BITS 64] and DEFAULT REL, and build.py assembles it with /usr/bin/nasm (alongside syscalls.asm). Its name follows the same extern "C" convention, so the C++ declaration in retaddrspoof.h links to the assembly global RetSpoofCall symbol.

The procedure is a two-stage trampoline:

  • Prologue / marshalling. It reserves 0x100 bytes of scratch (sub rsp, 0x100), saves the non-volatile registers (rsi, rdi, r12) into that scratch, and saves the target in r10 (mov r10, rcx) while loading r12 with the address of Fixup (lea r12, Fixup). After sub rsp, 0x200 for working space, it writes the gadget into the slot that will serve as the return address (mov [rsp], r8).
  • Argument shifting. If nArgs is 0, it jumps straight to the call. Otherwise it shifts every argument down by three: for up to four real arguments it moves r9 into rcx and pulls the stack arguments from [rsp+0x300+0x28], [rsp+0x300+0x30], and [rsp+0x300+0x38] into rdx/r8/r9 (the 0x300 accounts for the two sub rsp frames plus the caller's original spill). It moves all of them unconditionally because setting a register that a target does not use is harmless. For more than four arguments it uses rep movsq to copy the stack arguments down four slots (rsi/rdi pair with rcx = nArgs - 4), using an extra 0x18 offset because the fourth real argument was sitting in the seventh stack slot. The original rcx is restored afterward so the target still sees the first argument.
  • The spoofed call. CallFunction: jmp r10 jumps into the target. The target's own ret pops the gadget (planted at [rsp]) instead of a loader-frame return address, so the unwinder sees execution resume inside ntdll at a call r12 gadget. The gadget's call r12 then dispatches to Fixup (the handler already loaded in r12).
  • Fixup. Fixup restores the non-volatile registers from the saved scratch (rsi/rdi/r12 at [rsp+0x200+0x8/0x10/0x18]), unwinds the two reserved frames (add rsp, 0x300), and rets — returning to the actual caller of RetSpoofCall with the stack fully restored.

The following sequence diagram shows the full round trip for a wrapped call:

sequenceDiagram participant Caller as Loader module participant RSC as RetSpoofCall (retaddrspoof.asm) participant Tgt as Target function participant Gadget as ntdll call r12 (Gdgt) participant Fixup as Fixup handler Caller->>RSC: RetSpoofCall(Function, nArgs, Gdgt, args...) RSC->>RSC: shift args down 3, save rsi/rdi/r12 RSC->>RSC: plant Gdgt as return address (mov [rsp], r8) RSC->>Tgt: jmp r10 (target) Tgt-->>Gadget: ret to planted Gdgt (call r12) Gadget->>Fixup: call r12 (r12 = Fixup) Fixup->>Caller: restore regs + frame, ret to original caller

The target function's ret lands on the ntdll call r12 gadget (Gdgt), not a loader frame, and the gadget forwards to Fixup, which restores the loader's own stack frame before returning to the true caller.

Why this defeats EDR unwinding

Without spoofing, an unwinder walking the thread stack after, say, memcpy returns would see the loader's frames (main, AESDecrypt, etc.) as the return addresses. With spoofing, the return address of every wrapped call points into ntdll at a call r12 gadget, and the handler frames are the loader's own RetSpoofCall/Fixup internals, which contain no distinctive module/symbol that a signature would attribute to the loader. Because Gdgt is chosen randomly from up to 30 candidate gadget addresses, the exact return location varies, defeating naive "return address equals ntdll+X" heuristics.

Invariants and failure semantics

  • Gdgt must be resolved before any RetSpoofCall use. It is initialized as a global in Ghost.cpp before main() runs, so every module that externs it already has a valid gadget. FindROPGadget prints an error and returns NULL if ntdll's HMODULE is NULL or a signature check fails; in that degenerate case the planted return address would be NULL and the spoofed call would crash on the return, which is why the signatures are validated ahead of time.
  • The gadget must be call r12 and r12 must equal Fixup. FindROPGadget scans only for 41 FF D4, and the prologue loads r12 with Fixup immediately before jumping into the target, so the gadget's call r12 always transfers control to Fixup. Any change to the handler register or the gadget pattern must be mirrored on both sides.
  • Only executable ntdll sections are scanned. The IMAGE_SCN_CNT_CODE + IMAGE_SCN_MEM_EXECUTE filter guarantees the returned gadget address is in executable memory, so executing call r12 there is valid.
  • Assembly is NASM-only. retaddrspoof.asm cannot be consumed by MASM; build.py must assemble it with nasm into win64 object format, exactly like syscalls.asm.
  • The wrapper shifts exactly three slots. Every call to RetSpoofCall passes (Function, nArgs, Gdgt, args...) and the assembly shifts arguments down by three, so a caller that miscounts nArgs (or passes the wrong arity) would misalign stack arguments and corrupt the call. The header documents nArgs as the count of real target arguments, and the call sites throughout the project pass explicit counts (5 for read/protect, 2 for terminate, 11 for create-user-process) so the prologue lines the stack up correctly.

Shellcode Encryption & Memory Hiding (AES.h, allocator.h, rsrc.h)

Ghost keeps its shellcode from ever being observable on disk or in memory by composing three mechanisms into one main() phase (see the loader pipeline):

  1. rsrc.h / Resource.rc — retrieves the AES-encrypted shellcode from an embedded RCDATA resource that is disguised as an icon (.ico).
  2. AES.h — decrypts that ciphertext back into plaintext shellcode using the Windows BCrypt API in CBC mode with a 32-byte key and 16-byte IV.
  3. allocator.h — places the decrypted plaintext inside a very large, randomly-filled allocation at a random offset, so memory scanners do not see a contiguous, page-aligned shellcode blob (the Roshtyak technique).

Every API involved — the resource functions, every BCrypt call, the memory allocator, and the memcpy — is resolved by hash at runtime (functions.h) and invoked through RetSpoofCall with the global Gdgt ROP gadget, so no import table entry and no loader frame exposes either the shellcode or the cryptographic operation. See api-resolution-and-hashing and return-address-spoofing for those shared mechanisms.

The build-time half: encrypting and embedding the payload

Before any of the runtime code runs, build.py produces the on-disk disguise:

def aes_encrypt(data):
    key = generate_random_key(32)  # 256 bits
    iv = generate_random_key(16)   # 128 bits
    ...
    cipher = AES.new(key, AES.MODE_CBC, iv)
    encrypted_data = cipher.encrypt(pad(data, AES.block_size))
    return encrypted_data, key, iv
  • prepare_src_shellcode() → do_aes(SHELLCODE) reads the raw x64 shellcode binary, generates a fresh random 32-byte AES key and 16-byte IV per build, encrypts with AES-256-CBC (PKCS7 padding via pad), and writes the ciphertext to icon.ico.
  • It then rewrites Ghost.cpp by regex-replacing the unsigned char AesKey[] = {...}; and unsigned char AesIv[] = {...}; arrays with the newly generated key/IV.
  • build_resource() compiles Resource.rc, which embeds icon.ico as the IDR_RCDATA1 RCDATA resource, into build/Resource.o.
  • The link step (link()) combines the resource object, the NASM objects, and Ghost.o into Ghost.exe.

The result is that the only encrypted payload on disk rides inside a resource that Windows shows as an .ico icon, and the decryption key changes every build so old static signatures for the key never persist.

flowchart TD S["shellcode.bin (raw x64)"] --> E["build.py aes_encrypt: AES-256-CBC + random 32B key + 16B IV"] E --> I["icon.ico (ciphertext)"] E --> R["rewrite AesKey/AesIv arrays in Ghost.cpp"] I --> RC["Resource.rc: IDR_RCDATA1 RCDATA icon.ico"] RC --> RO["windres -> Resource.o"] RO --> EXE["link -> Ghost.exe"] R --> G["Ghost.cpp -> Ghost.o"] G --> EXE

Runtime step 1: GetFromRc — extracting the resource (rsrc.h)

GetFromRc(DWORD& size, PVOID& ptr) in rsrc.h pulls the encrypted payload out of the embedded resource using the classic Windows resource API, with every call hash-resolved and ret-spoofed:

  1. FindResourceW(NULL, MAKEINTRESOURCEW(IDR_RCDATA1), RT_RCDATA) — locates the resource by ID IDR_RCDATA1 (defined as 101 in resource1.h) of type RT_RCDATA.
  2. LoadResource(NULL, hResource) — loads it into global memory.
  3. LockResource(hGlobal) — returns a pointer to the loaded resource bytes.
  4. SizeofResource(NULL, hResource) — returns its byte size.

All four are resolved in functions.h from kernelbase.dll via hash (e_FindResourceW, e_LoadResource, e_LockResource, e_SizeofResource) and each passed through RetSpoofCall((void*)e_..., Gdgt, ...). The function writes the resource base into ptr and its size into size, returning 0 on success (it stops and prints a failure line if any step returns NULL, though it does not hard-abort).

IDR_RCDATA1 RCDATA "icon.ico" in Resource.rc is what makes FindResourceW(..., RT_RCDATA) find the icon file's bytes at runtime — the encrypted shellcode is thus buried in what appears to be an icon resource.

main() then copies those bytes into a heap buffer (AesCipherText) with a ret-spoofed memcpy and feeds them to the decryptor.

Runtime step 2: AESDecrypt — the BCrypt decryption flow (AES.h)

AESDecrypt (the public wrapper) validates its inputs, fills an AES struct with the key, IV, ciphertext, and ciphertext size, and calls InternalAESDecrypt.

InternalAESDecrypt runs the full BCrypt symmetric-decryption sequence against bcrypt.dll, where every call is hash-resolved (e_BCrypt* in functions.h) and wrapped in RetSpoofCall:

  1. BCryptOpenAlgorithmProvider(&hAlgorithm, BCRYPT_AES_ALGORITHM, NULL, 0) — opens an AES algorithm handle.
  2. BCryptGetProperty(hAlgorithm, BCRYPT_OBJECT_LENGTH, ...) — queries cbKeyObject (the key-object buffer size) and BCRYPT_BLOCK_LENGTH (block size).
  3. It validates the block size equals 16 and allocates the key object on the heap with malloc + RtlSecureZeroMemory.
  4. BCryptSetProperty(hAlgorithm, BCRYPT_CHAINING_MODE, BCRYPT_CHAIN_MODE_CBC, ...) — switches the algorithm to CBC chaining mode.
  5. BCryptGenerateSymmetricKey(hAlgorithm, &hKeyHandle, pbKeyObject, cbKeyObject, KEY, KEYSIZE) — builds the key object from the 32-byte key (KEYSIZE = 32).
  6. Two-pass BCryptDecrypt: the first call passes NULL/null output pointers with BCRYPT_BLOCK_PADDING to learn the decrypted size (cbPlainText); the second allocates a heap buffer and decrypts the ciphertext in place with the 16-byte IV (IVSIZE = 16), returning the plaintext.

On success the plaintext pointer and size are written back into the AES struct, and AESDecrypt returns them through its pPlaintTextData / pPlaintTextSize out-parameters. Cleanup (_CLEANUP) destroys the key (BCryptDestroyKey), closes the algorithm (BCryptCloseAlgorithmProvider), and frees the key object; the plaintext buffer is only attached to the struct when the operation succeeded.

The throughput of this phase in main():

decryption = AESDecrypt(AesCipherText, ResourceSize, AesKey, AesIv, &pPlainBuffer, &PlainBufferSize);
if (!decryption) { std::cout << "[+] Decryption UnSuccessful" << std::endl; return -1; }

So a failed decryption aborts the loader before any allocation or payload execution.

Runtime step 3: allocate_large_page / place_data_rand — Roshtyak hiding (allocator.h)

allocate_large_page(SIZE_T cbPageSize) creates a camouflage region large enough that the real payload is only a tiny fraction of it:

  • pCtx->uSize = ALIGN_PAGE(cbPageSize * FACTOR) with FACTOR = 2048 and ALIGN_PAGE(n) = ((n + 0x1000) & ~(0x1000)) — the region is 2048× the plaintext size, rounded up to a page.
  • It sets lpPage = nullptr (explicitly, because the NT API requires a NULL base pointer for allocation), then calls NtAllocateVirtualMemory (ret-spoofed, SELF_HANDLE) with MEM_COMMIT | MEM_RESERVE and PAGE_READWRITE.
  • It fills the whole region with cryptographic random noise via SystemFunction036 (i.e. RtlGenRandom).
  • It picks a random byte offset dwOffset = RANDOM_NUMB(0, uSize) and computes lpData = (BYTE*)lpPage + dwOffset — the random slot where the payload will live.
  • The result is returned in a LARGE_PAGE_INFORMATION context; on allocation failure it returns NULL (via NTAPI_VALIDATE_RETURN2NULL).

place_data_rand(pCtx, pbBuffer, cbBuffer) then copies the decrypted plaintext into that random slot with a ret-spoofed memcpy. Because the payload is buried among tens or hundreds of megabytes of RtlGenRandom bytes at a non-page-aligned, random offset, a naive memory scan for a contiguous shellcode signature finds nothing, and the allocation itself looks like ordinary random data.

In main(), once the payload is placed, the now-unneeded ciphertext copy and plaintext heap buffer are immediately freed:

pLPI = allocate_large_page(PlainBufferSize);
place_data_rand(pLPI, (PBYTE)pPlainBuffer, PlainBufferSize);
free(AesCipherText);
delete[] pPlainBuffer;

so the sole remaining copy of the shellcode lives only inside the camouflaged random allocation. Later the pipeline makes the whole large page executable (PAGE_EXECUTE_READ) and runs the payload fiber from pLPI->lpData, but that is the responsibility of the loader pipeline and fiber-based-stack-hiding, not this page.

    M->>R: GetFromRc(ResourceSize, ptr)
    R-->>M: ptr = RCDATA bytes (ciphertext), size
    M->>M: memcpy -> AesCipherText (heap)
    M->>A: AESDecrypt(AesCipherText, ..., AesKey, AesIv)
    A-->>M: pPlainBuffer + PlainBufferSize
    M->>AL: allocate_large_page(PlainBufferSize)
    AL-->>M: pLPI (large random page, random offset)
    M->>AL: place_data_rand(pLPI, plaintext, size)
    M->>M: free(AesCipherText); delete[] pPlainBuffer

Runtime composition: resource extraction feeds the BCrypt decryptor, whose plaintext is camouflaged into a large random allocation — after which the transient ciphertext and plaintext buffers are freed.

Key data structures

  • AES (in AES.h): carries pPlainText/plainTextSize (output) and pCipherText/CipherSize (input), plus the KEY (32 bytes) and IV (16 bytes). KEYSIZE and IVSIZE are fixed at 32 and 16.
  • LARGE_PAGE_INFORMATION (in allocator.h): records the random dwOffset, the region uSize, the base lpPage, and lpData (the actual payload location).

Configuration & operational notes

  • Key/IV are per-build. AesKey/AesIv are hardcoded arrays in Ghost.cpp but build.py regenerates them every build, so they are not static credentials.
  • The resource is an .ico. Resource.rc declares IDR_RCDATA1 RCDATA "icon.ico", and build.py writes the encrypted shellcode into icon.ico; the loader treats it as RT_RCDATA at runtime, so the on-disk artifact presents as an icon while actually carrying ciphertext.
  • Hash-resolved + ret-spoofed throughout. None of the resource, BCrypt, allocator, or memcpy calls appear as link-time imports; all resolve through GetFunctionAddressH and execute through RetSpoofCall with Gdgt. This composes the disk hiding with the runtime stack-hiding and API-resolution mechanisms in the rest of the project.
  • Failure semantics: AESDecrypt returns FALSE on any invalid input or failed BCrypt step, and main() aborts (return -1); allocate_large_page returns NULL if the allocation fails. The decrypted data only becomes the payload fiber entry point later in the pipeline, so a failure here stops the loader before execution.

Relationships

  • loader-pipeline — the three mechanisms are one phase of main()'s startup sequence.
  • api-resolution-and-hashing — every API here is resolved at runtime via functions.h / resolvers.h instead of being imported.
  • return-address-spoofing — every call in these three modules runs through RetSpoofCall with the shared Gdgt.
  • fiber-based-stack-hiding — what happens to the hidden payload after it is made executable and run as a fiber.

Ghost Loader Wiki Quickstart

Ghost is a standalone, evasive Windows shellcode loader written in C++ with NASM assembly. It loads an AES-encrypted x64 shellcode payload and executes it while evading the detection techniques a typical EDR uses: kernel callbacks, stack unwinding, memory scanning, API hooking, and ETW. It is not a library — it is a complete program that starts from main() in Ghost.cpp and never returns.

The main entrypoint is Ghost.cpp. Its main() calls nearly every evasion mechanism in sequence: it unhooks ntdll, patches ETW, decrypts and hides the payload, then runs the payload on a fiber while the loader thread performs an invisible kernel-safe sleep loop.

A compact mental model

flowchart TD G["Ghost.cpp main"] --> H["unhook ntdll"] G --> E["patch ETW"] G --> D["decrypt AES payload from resource"] D --> C["camouflage payload in large random allocation"] C --> F["set up fiber pair + Sleep hook"] F --> P["run payload on fiber"] P --> S["Sleep hook switches to loader fiber"] S --> W["invisible event-based delay"] W --> P

High-level pipeline: every operation revolves around main() in Ghost.cpp, which composes unhooking, ETW patching, shellcode decryption/hiding, and the fiber-based sleep loop shown in detail on the loader pipeline page.

Three cross-cutting mechanisms make this architecture readable:

  • RetSpoofCall — the variadic assembly wrapper (in retaddrspoof.asm) that every module uses to hide call stacks. Nearly every API, NT call, and indirect syscall in the project is invoked through it, along with the shared Gdgt ROP gadget pointer.
  • Gdgt — a randomly chosen call r12 ROP gadget from ntdll, declared once in Ghost.cpp and shared across all modules so every spoofed call returns through a legitimate ntdll gadget.
  • functions.h + resolvers.h — the runtime API resolution layer. Functions are not imported at link time; they are resolved by walking the PEB and parsing the PE export table with a custom hash, so there is no import table for an EDR to inspect.

How to navigate the wiki

The wiki is organized into three directories that map cleanly onto how you read the code:

  • /openwiki/architecture/ — end-to-end flows and shared foundations. Start with the loader pipeline for the canonical order of operations, then read shared types, structures & constants for the type definitions, NT structs, and macros everything depends on.
  • /openwiki/concepts/ — the individual evasion mechanisms, each documented on its own page because they are independently testable techniques. These are the building blocks the pipeline composes.
  • /openwiki/workflows/ — build and operational procedures. See build & deployment for how the binary is produced.

Build & Deployment Workflow (build.py)

build.py is the automated builder that converts a raw x64 shellcode .bin file into a deployable Ghost.exe. It is the only way the loader is produced: it generates a per-build AES key/IV, encrypts the shellcode into an .ico file, patches the key/IV into Ghost.cpp, compiles the C++ and the two NASM stubs, compiles the Win32 resource, and links everything into Ghost.exe — all on Linux using the MinGW cross-toolchain.

The build script deliberately does not run on Windows. It requires Python 3, pycryptodome, the MinGW cross-compiler (x86_64-w64-mingw32-g++), the MinGW windres, and NASM.

Toolchain and key constants

The script hardcodes the host toolchain paths and compile/link flags at the top of build.py so a future user can adjust them in one place:

  • WINDRES = "/usr/bin/x86_64-w64-mingw32-windres"
  • NASM = "/usr/bin/nasm"
  • MinGW = "/usr/bin/x86_64-w64-mingw32-g++"
  • MinGW_FLAGS = -fmerge-all-constants -fexpensive-optimizations -finline-functions -fno-stack-protector -fno-unroll-loops -fno-exceptions -fno-rtti -Wpointer-arith -fpermissive -w -static-libgcc -static-libstdc++
  • MinGW_LINK_FLAGS = same base flags plus -flto -s -Wl,--gc-sections -Wl,--strip-all (i.e. link-time optimization, strip symbols, and section garbage collection).

The crucial difference is that MinGW_LINK_FLAGS adds -flto, -s, --gc-sections, and --strip-all to the object-compile flags, so the final Ghost.exe is stripped and dead code is removed at link time.

All intermediate artifacts are written to a $CUR_DIR/build folder, which the script creates if it does not already exist (with a [BUILD] log line either way).

Usage

python3 build.py --shellcode shellcode.bin
# or, equivalently
python3 build.py -i shellcode.bin

--shellcode (alias -i) is the only required argument; the raw x64 shellcode binary is passed on the command line. The README confirms the canonical invocation is python3 build.py -i shellcode.bin.

Pipeline

The main block runs the five stages in a fixed order:

flowchart TD A["build_assembly()"] --> B["prepare_src_shellcode()"] B --> C["build_resource()"] C --> D["build_cpp_src()"] D --> E["link()"]

The five build stages of build.py, executed in sequence from the __main__ block.

flowchart TD ra["retaddrspoof.asm"] --> nasm["NASM -f win64"] sa["syscalls.asm"] --> nasm nasm --> ro["build/retaddrspoof.o"] nasm --> so["build/syscalls.o"] sc["shellcode.bin (raw x64)"] --> aes["prepare_src_shellcode: aes_encrypt (AES-256-CBC + random 32B key + 16B IV)"] aes --> ico["icon.ico (ciphertext)"] aes --> gpatch["regex-substitute AesKey/AesIv into Ghost.cpp"] ico --> rc["Resource.rc: IDR_RCDATA1 RCDATA icon.ico"] rc --> wr["windres -i Resource.rc"] wr --> reso["build/Resource.o"] gpatch --> gcpp["Ghost.cpp"] gcpp --> mingw["MinGW g++ -c MinGW_FLAGS"] mingw --> go["build/Ghost.o"] ro --> link["link(): MinGW LINK_FLAGS"] so --> link reso --> link go --> link link --> exe["build/Ghost.exe"]

Full build pipeline: NASM compiles the two assembly stubs, the shellcode is AES-encrypted into icon.ico and its key/IV injected into Ghost.cpp, windres compiles the resource, MinGW compiles the C++, and link() combines all four objects into Ghost.exe.

1. build_assembly() — NASM stubs

build_assembly() runs NASM twice, once per assembly stub, in -f win64 format:

nasm -f win64 retaddrspoof.asm -o build/retaddrspoof.o
nasm -f win64 syscalls.asm -o build/syscalls.o

Both files are declared NASM-only (they each begin with "NOT MASM, this file is in NASM syntax and can only be assembled with NASM assembler"). retaddrspoof.asm exports RetSpoofCall (the ROP-gadget return-address-spoofing wrapper used throughout the loader), while syscalls.asm exports the indirect syscall trampolines SysNtCreateUserProcess, SysNtReadVirtualMemory, SysNtProtectVirtualMemory, and SysNtTerminateProcess. Each NASM invocation captures stderr; if either produces any stderr output the script prints the failing command and exit()s immediately.

2. prepare_src_shellcode() — encrypt and inject key/IV

prepare_src_shellcode() does the encryption and source patching:

  1. do_aes(SHELLCODE) reads the raw shellcode .bin and calls aes_encrypt(data).
  2. aes_encrypt() generates a fresh random 32-byte AES key (generate_random_key(32), 256-bit) and a fresh random 16-byte IV (generate_random_key(16), 128-bit), then encrypts with AES-256-CBC using Crypto.Cipher.AES with PKCS7 padding (pad(data, AES.block_size)).
  3. The ciphertext is written to icon.ico in the repo root.
  4. The key/IV are formatted as unsigned char AesKey[] = { 0x.., ... }; and unsigned char AesIv[] = { ... }; C array initializers.
  5. Ghost.cpp is read, and two regexes (unsigned char AesKey\[\] = \{.*?\}; and unsigned char AesIv\[\] = \{.*?\};) substitute the newly generated arrays into the source. The patched source is written back over Ghost.cpp.

This is the mechanism that makes the per-build AES credentials unique and keeps the key from being a static signature.

3. build_resource() — compile the Win32 resource

build_resource() runs windres on the resource script:

x86_64-w64-mingw32-windres -i Resource.rc -o build/Resource.o

Resource.rc includes resource1.h (which defines IDR_RCDATA1 101) and declares IDR_RCDATA1 RCDATA "icon.ico". Because prepare_src_shellcode() wrote the encrypted shellcode into icon.ico, compiling this resource embeds the ciphertext into the executable as a resource that Windows presents as an icon — part of the on-disk evasion strategy. At runtime the loader retrieves these bytes via FindResourceW/RT_RCDATA and decrypts them (see shellcode-encryption-and-hiding).

4. build_cpp_src() — compile the C++ loader

build_cpp_src() compiles the patched Ghost.cpp with the MinGW cross-compiler:

x86_64-w64-mingw32-g++ -c Ghost.cpp MinGW_FLAGS -o build/Ghost.o

This produces build/Ghost.o from the single translation unit that now carries the freshly injected AesKey/AesIv.

5. link() — produce Ghost.exe

link() links all four objects into the final executable:

x86_64-w64-mingw32-g++ build/syscalls.o build/retaddrspoof.o build/Resource.o build/Ghost.o MinGW_LINK_FLAGS -o build/Ghost.exe

The link step applies the link-only flags (-flto, -s, --gc-sections, --strip-all) and emits build/Ghost.exe.

Failure semantics and validation

  • There are no tests. The script's only validation is capturing each subprocess's stderr.
  • Every stage runs its tool with stdout suppressed (stdout=subprocess.DEVNULL) and stderr captured (stderr=subprocess.PIPE), then checks if (cmd.stderr:.
  • On any non-empty stderr, the script prints an [ERROR] line, prints the exact command that was used (the [i] command used: line), and calls exit() immediately — halting the build at the first failure stage and preserving the complete failure output for diagnosis.
  • Each stage is a hard prerequisite for the next: assembly objects must exist before linking, the resource must embed the fresh icon.ico, and Ghost.cpp must carry the key/IV that encrypted that icon.ico in the same build. Because of this ordering, a failure at any stage stops the build before a mismatched or incomplete executable can be produced.

Operations and deployment notes

  • Host Linux only. The builder relies on absolute /usr/bin/ paths for the MinGW compiler, windres, and nasm, and on python3 + pycryptodome — it will not run on Windows.
  • The embedded .ico is intentional. The encrypted shellcode is stored as an icon resource (IDR_RCDATA1 RCDATA "icon.ico"), matching the loader's RT_RCDATA extraction at runtime. This is a deliberate evasion: the on-disk artifact presents as an icon while carrying ciphertext.
  • Per-build key/IV. Because prepare_src_shellcode() regenerates the AES key and IV and rewrites Ghost.cpp on every run, no static key persists across builds, defeating signature-based detection of a fixed credential.
  • Outputs. build/Ghost.exe is the deployable artifact; build/retaddrspoof.o, build/syscalls.o, build/Resource.o, and build/Ghost.o are intermediate objects, and icon.ico is the (overwritten per build) embedded ciphertext source.
