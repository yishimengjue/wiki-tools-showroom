Project Introduction

Ghost is a Windows-based shellcode loader and evasion framework designed to demonstrate advanced techniques for bypassing security controls, including ETW patching, NTDLL unhooking, return address spoofing, and indirect syscalls. The project combines assembly-level syscall stubs with C++ orchestration to create a stealthy execution pipeline. The build system automates assembly, resource compilation, AES encryption of shellcode, and linking into a final executable.

The project is organized into modular headers, each responsible for a distinct capability: process creation via NtCreateUserProcess, memory allocation using large random pages, fiber-based sleep obfuscation, and API resolution through custom hashing. The overall flow begins with encrypted shellcode embedded as a resource, which is decrypted at runtime and executed within a protected environment.

Sources: build.py, defs.h, structs.h, functions.h, resolvers.h, ntprocessapi.h, unhook.h, hook.h, etw.h, allocator.h, rsrc.h

Build System Overview

The build pipeline is orchestrated by build.py, which compiles assembly files, encrypts shellcode, builds resources, compiles the C++ source, and links everything into an executable. The script uses NASM for assembly, MinGW for C++ compilation, and Windres for resource compilation.

The build sequence is as follows:

if __name__ == '__main__':
    build_assembly()
    prepare_src_shellcode()
    build_resource()
    build_cpp_src()
    link()

Conclusion

Ghost demonstrates a comprehensive approach to Windows evasion, combining multiple advanced techniques into a single modular framework. The project's architecture separates concerns into distinct headers, each handling a specific aspect of the evasion chain: API resolution, syscall invocation, process manipulation, memory obfuscation, and execution control. The build system automates the entire process from shellcode encryption to final executable linking, making it a complete example of modern Windows shellcode loader design.

The use of indirect syscalls, return address spoofing, and custom hashing throughout the codebase ensures that the final executable has minimal static indicators, while the runtime techniques (ETW patching, NTDLL unhooking, fiber-based sleep) address common detection mechanisms. This project serves as both a functional tool and an educational resource for understanding Windows internals and evasion techniques.

Detection Techniques and Evasion Strategy

Introduction

Ghost is a sophisticated proof-of-concept malware loader that implements a comprehensive suite of detection evasion techniques designed to bypass modern Endpoint Detection and Response (EDR) solutions. The project's primary objective is to demonstrate how advanced evasion strategies—including return address spoofing, indirect syscalls, API hashing, process unhooking, ETW patching, and fiber-based callstack hiding—can be combined to create a stealthy execution chain that avoids both static and behavioral detection.

The evasion strategy is organized around several complementary layers: static evasion (custom API resolution and shellcode encryption), runtime evasion (NTDLL unhooking and ETW patching), execution evasion (suspended process creation and indirect syscalls), and callstack obfuscation (return address spoofing and fiber switching). Each layer is implemented in dedicated header files that work together through a shared infrastructure of custom function pointers, hashing utilities, and a global gadget pointer (Gdgt) used for return address spoofing.

Sources: README.md, defs.h, retaddrspoof.h

Return Address Spoofing

Core Mechanism

The RetSpoofCall function is an assembly-implemented variadic function that spoofs the return address of any API call by using a ROP gadget (call r12) found in NTDLL. This technique ensures that when an EDR hooks a function and inspects the callstack, it sees a legitimate return address within NTDLL rather than the actual caller in the Ghost binary.

ROP Gadget Discovery

The FindROPGadget function scans NTDLL's executable sections for the byte pattern 41 FF D4 (which corresponds to call r12). It collects up to MAX_GADGETS (30) valid gadgets and returns a random one each time to avoid predictable patterns:

Ghost is a Windows shellcode loader that implements a multi-stage execution pipeline designed for stealth and evasion of Endpoint Detection and Response (EDR) systems. Fiber-Based Execution Model

Introduction

The Fiber-Based Execution Model is a core evasion mechanism within the Ghost project, designed to hide the execution stack of a beacon (e.g., Cobalt Strike) during its sleep cycles. The model leverages Windows Fibers to create an execution context that can be switched away from the main thread's stack, effectively obscuring the beacon's call stack from EDR/AV inspection tools that scan memory during idle periods.

The system operates by hooking the Sleep/SleepEx functions used by the beacon and redirecting them to a custom fiber-switching routine. When the beacon attempts to sleep, the execution context is switched to a separate fiber whose stack contains only benign, non-suspicious frames. This allows the beacon to remain dormant without exposing its true stack layout to security products. The implementation is tightly integrated with return address spoofing and indirect syscalls to further obscure the execution flow.

  • 49 BA + 8-byte address: mov r10, <address> (loads the redirection function address into r10)

  1. Patches the hook bytes with the target redirection function address
  2. Changes the memory protection of the target function to PAGE_READWRITE
  3. Copies the hook bytes over the function prologue
  4. Restores the original memory protection

Return Address Spoofing Mechanism

Introduction

The Return Address Spoofing Mechanism is a core defensive technique implemented in the Ghost project to evade detection by Endpoint Detection and Response (EDR) systems. It works by manipulating the return address on the call stack when invoking sensitive Windows API functions, making it appear as though the calls originate from legitimate system libraries (such as ntdll.dll) rather than from the Ghost payload itself. This mechanism is built around a variadic assembly function called RetSpoofCall, which is used throughout the project for virtually every sensitive operation, including memory allocation, process creation, API resolution, and ETW patching.

The mechanism is tightly integrated with the project's broader evasion strategy, which includes indirect syscalls, API hashing, and fiber-based sleep obfuscation. By spoofing return addresses, Ghost ensures that stack-walking-based detection tools cannot trace malicious calls back to the payload's code, significantly increasing the stealth of the implant. The following sections detail the architecture, implementation, and usage of this mechanism across the codebase.

Sources: retaddrspoof.h, retaddrspoof.asm, README.md

Architecture Overview

The Return Address Spoofing Mechanism consists of three primary components:

  1. The Assembly Function RetSpoofCall: A variadic function written in assembly that handles the actual stack manipulation and call redirection.
  2. The ROP Gadget Finder (FindROPGadget): A C++ function that locates a call r12 gadget in ntdll.dll to be used as the return address target.
  3. The Global Gadget Pointer (Gdgt): A project-wide variable that stores the address of the found ROP gadget, passed to every RetSpoofCall invocation.

The data flow is as follows: at initialization, FindROPGadget scans ntdll.dll for a valid call r12 gadget. The address of this gadget is stored in the global Gdgt variable. Whenever the payload needs to call a Windows API function, it invokes RetSpoofCall with the function pointer, the number of arguments, the gadget address, and the actual arguments. The assembly function then executes the target function but ensures that the return address on the stack points to the ROP gadget in ntdll.dll, effectively hiding the true caller.

The RetSpoofCall Assembly Function

Declaration and Signature

The RetSpoofCall function is declared as an external C function in retaddrspoof.h:

extern "C" void* RetSpoofCall(void* Function, unsigned long long nArgs, void* r12_gadget, void* argN, ...);

Sources: retaddrspoof.h

The function takes:

  • Function: A pointer to the target API function to invoke.
  • nArgs: The number of arguments to pass to the target function.
  • r12_gadget: The address of the ROP gadget (the call r12 instruction) to use as the return address.
  • argN, ...: The variadic arguments to forward to the target function.

The function returns a void* so that the result can be cast to any type, allowing it to be used with APIs of different return types.

Assembly Implementation

The assembly implementation in retaddrspoof.asm performs the following steps:

  1. Saves the current register state.
  2. Copies the variadic arguments from the stack into the appropriate registers (RCX, RDX, R8, R9) and the stack for additional arguments.
  3. Places the r12_gadget address into the R12 register.
  4. Calls the target function, but before doing so, manipulates the stack so that the return address is the ROP gadget.
  5. After the target function returns, restores the register state and returns to the caller.

The key insight is that the call r12 gadget, when executed, will jump to the address stored in R12. By setting R12 to a legitimate function pointer (or a ret instruction), the gadget acts as a trampoline that returns control to the spoofed caller, making the stack trace appear as if the call came from within ntdll.dll.

ROP Gadget Discovery

The FindROPGadget Function

The FindROPGadget function is responsible for locating a suitable call r12 gadget within the executable code section of ntdll.dll. This function is defined in retaddrspoof.h and performs the following steps:

  1. Obtains the base address of ntdll.dll from the global hNT handle.
  2. Validates the DOS and NT headers of the module.
  3. Iterates through the PE sections to find the executable code section.
  4. Scans the code section for the byte pattern 0x41 0xFF 0xD4, which corresponds to the call r12 instruction.
  5. Collects up to MAX_GADGETS (30) valid gadget addresses.
  6. Returns a random gadget address from the collected list to avoid predictability.

The validation of a gadget is performed by the IsValidGadgetx64 function:

static BOOL IsValidGadgetx64(PBYTE pbAddress)
{
    return *pbAddress == 0x41 && *(pbAddress + 1) == 0xFF && *(pbAddress + 2) == 0xD4;
}

Sources: retaddrspoof.h

Randomization

The function uses the GEN_RAND macro to select a random gadget from the collected list:

#define GEN_RAND(min, max) (rand() % (max + 1 - min) + min)

This randomization ensures that the same gadget is not used consistently, making detection more difficult.

Introduction

The allocate_large_page() function implements the core memory hiding technique. It performs the following operations:

Hash Generation: The WEIRDHASHA Algorithm

The hash algorithm used throughout the project is defined in hash.h. It combines a custom string-to-DWORD conversion with a prime-based iterative hash to produce a unique identifier for each API name or module path.

Core Functions

The algorithm consists of two main functions:

  1. getStringAsDWORD: Converts a string into a DWORD by iterating over each character and applying the formula value = (value << 5) + value + str[i]. This is a variant of the classic DJB2 hash, where each character is combined with the accumulated value using a left-shift-by-5 plus addition.

  2. WEIRDHASHA: Takes a string and an iteration count. It initializes a hash to the prime number 5381, then repeatedly applies Hash = (Hash << 5) + Hash (equivalent to multiplying by 33) for the specified number of iterations. The final hash is computed as Hash * dwString + lstrlenA(String), where dwString is the result of getStringAsDWORD.

DWORD WEIRDHASHA(_In_ const char* String, SIZE_T Iterations) {
    SIZE_T Index = 0;
    DWORD Hash = 5381;  // Starting with a prime number
    SIZE_T Length = Iterations;

    // Compute the hash with the given number of iterations
    while (Index != Length) {
        Hash = (Hash << 5) + Hash;  // Equivalent to Hash * 33
        Index++;
    }

    // Obtain DWORD from the first 4 characters of the string
    DWORD dwString = getStringAsDWORD(String);

    // Multiply the hash by this DWORD value
    return Hash * dwString + lstrlenA(String);
}

The GetLoadedDllHandleH function in resolvers.h implements a PEB (Process Environment Block) walk to find loaded modules by their hash. This approach avoids calling GetModuleHandle or LoadLibrary, which could be hooked or monitored.

The function starts by reading the PEB from the Thread Information Block (TEB) using __readgsqword(96), which retrieves the PEB address on x64 systems.             i++;

    return NULL;
}

Function Resolution: Export Table Parsing

The GetFunctionAddressH function in resolvers.h implements a custom GetProcAddress replacement by manually parsing the PE export directory of a given DLL.

Export Directory Walk

The function takes a DLL handle and a hash, then:

  1. Validates the DOS and NT signatures.
  2. Retrieves the export directory RVA from the optional header's data directory.
  3. Iterates through the AddressOfNames array, computing the hash of each exported function name.
  4. When a match is found, uses the corresponding ordinal to index into AddressOfFunctions and returns the function address.
FARPROC GetFunctionAddressH(HMODULE DllHandle, DWORD dwHash) {
    uintptr_t DllBase = reinterpret_cast<uintptr_t>(DllHandle);
    PIMAGE_DOS_HEADER dos = (PIMAGE_DOS_HEADER)DllBase;
    // ... signature checks ...
    PIMAGE_NT_HEADERS ntheaders = reinterpret_cast<PIMAGE_NT_HEADERS>(DllBase + dos->e_lfanew);
    IMAGE_OPTIONAL_HEADER64 OptionalHeader64 = ntheaders->OptionalHeader;
    DWORD ExportDirRva = OptionalHeader64.DataDirectory[IMAGE_DIRECTORY_ENTRY_EXPORT].VirtualAddress;
    PIMAGE_EXPORT_DIRECTORY pExportDirectory = reinterpret_cast<PIMAGE_EXPORT_DIRECTORY>(DllBase + ExportDirRva);
    PDWORD AddressOfNames = reinterpret_cast<PDWORD>(DllBase + pExportDirectory->AddressOfNames);
    PDWORD AddressOfFunctions = reinterpret_cast<PDWORD>(DllBase + pExportDirectory->AddressOfFunctions);
    PWORD AddressOfOrdinals = reinterpret_cast<PWORD>(DllBase + pExportDirectory->AddressOfNameOrdinals);

    for (int i = 0; i < pExportDirectory->NumberOfNames; i++) {
        char* Name = reinterpret_cast<char*>(DllBase + AddressOfNames[i]);
        if (dwHash == WEIRDHASHA(Name, 27)) {
            FARPROC Function = reinterpret_cast<FARPROC>(DllBase + AddressOfFunctions[AddressOfOrdinals[i]]);
            return Function;
        }
    }
    return NULL;
}

Shellcode Encryption and Decryption Pipeline

Introduction

The Ghost loader implements a comprehensive shellcode encryption and decryption pipeline designed to protect payloads both at rest and during execution. The pipeline consists of two primary phases: an offline build phase (implemented in Python) that encrypts raw shellcode with AES-256-CBC and embeds it as a resource, and a runtime phase (implemented in C++) that retrieves, decrypts, and executes the payload while employing advanced evasion techniques such as return address spoofing, indirect syscalls, and NTDLL unhooking.

The build script generates a random AES key and IV for each build, ensuring unique encryption per compilation. At runtime, the loader retrieves the encrypted payload from the executable's resources, decrypts it using the BCrypt API (with all cryptographic calls wrapped in return address spoofing), and places the decrypted shellcode into a randomly allocated large memory region filled with cryptographic garbage—a technique inspired by the Roshtiak APT group.

Security Considerations

The resource embedding and extraction mechanism provides several security benefits:

  1. Encryption at Rest: The shellcode is never stored in plaintext on disk. The icon.ico file contains AES-encrypted data, and the decryption key is compiled into the binary.
