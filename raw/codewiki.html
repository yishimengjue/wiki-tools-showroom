Ghost Repository Architecture

Ghost is a Windows x64 shellcode loader whose build pipeline encrypts a payload into a PE resource and whose runtime decrypts and executes that payload inside a fiber. The implementation concentrates on reducing conventional user-mode visibility through hashed API resolution, indirect system calls, return-address spoofing, ntdll restoration, ETW patching, randomized memory placement, and fiber switching during payload sleep periods.

This document describes the repository as a single module because the supplied module tree contains no child modules. Component names below therefore refer directly to source files rather than to separate module documentation.

Security context: This is architecture documentation for a dual-use offensive-security codebase. The behaviors described include in-memory code execution and deliberate interference with monitoring facilities. Use and test it only in an authorized environment.

System Context

Ghost has two distinct execution environments:

  • Build host: Linux with Python, PyCryptodome, NASM, MinGW-w64, and windres.
  • Runtime host: 64-bit Windows with ntdll.dll, kernelbase.dll, bcrypt.dll, the native process APIs used by the loader, and a payload compatible with the loader's fiber/sleep assumptions.

The build host transforms raw x64 shellcode into an encrypted resource and compiles the loader. The Windows executable reverses that transformation, prepares its process, places the plaintext in a randomized allocation, and dispatches it as a fiber.

Architectural Overview

Ghost.cpp is the composition root. Most functionality is implemented as definitions in headers and is compiled into the single Ghost.cpp translation unit. functions.h initializes resolved API pointers and indirect-syscall metadata as global state before main runs. Gdgt, initialized by FindROPGadget, supplies the shared call r12 gadget used by RetSpoofCall throughout the repository.

Build-Time Pipeline

The builder is both a packager and a cross-compilation driver. It expects --shellcode/-i to identify an x64 binary payload and assumes the current working directory is the repository root.

flowchart TD Start[Run build.py with shellcode path] Assemble[Assemble retaddrspoof.asm and syscalls.asm] Read[Read shellcode bytes] Keys[Generate 32 byte key and 16 byte IV] Encrypt[AES CBC encrypt with PKCS padding] Icon[Write ciphertext as icon.ico] Rewrite[Replace AesKey and AesIv arrays in Ghost.cpp] Windres[Compile Resource.rc] Compile[Cross compile Ghost.cpp] Link[Link all objects] Output[build Ghost.exe] Start --> Assemble Assemble --> Read Read --> Keys Keys --> Encrypt Encrypt --> Icon Keys --> Rewrite Icon --> Windres Rewrite --> Compile Windres --> Link Compile --> Link Assemble --> Link Link --> Output

Builder Components

  • generate_random_key(length) delegates key and IV generation to Crypto.Random.get_random_bytes.
  • aes_encrypt(data) creates a fresh 256-bit key and 128-bit IV, encrypts with AES-CBC and block padding, and formats the same key material as C arrays.
  • do_aes(inputfile) reads the payload and writes ciphertext to icon.ico.
  • prepare_src_shellcode() uses regular expressions to replace the AesKey and AesIv definitions in Ghost.cpp.
  • build_assembly() assembles the return-spoofing and syscall stubs as Win64 object files.
  • build_resource() compiles Resource.rc; resource ID IDR_RCDATA1 points at the generated icon.ico file as raw RCDATA.
  • build_cpp_src() compiles the single C++ translation unit with MinGW-w64.
  • link() combines the two assembly objects, resource object, and C++ object into build/Ghost.exe.

The encrypted file is named icon.ico, but it is not treated as an icon. It is opaque AES ciphertext embedded under an RCDATA resource type.

prepare_src_shellcode() modifies Ghost.cpp in place, while do_aes() creates or overwrites icon.ico. Consequently, a build changes tracked source material and leaves payload-specific secrets in the generated source and executable.

Runtime Initialization and API Resolution

Before main, definitions in functions.h initialize key global handles and pointers:

  1. hNT is found by walking the current process PEB and matching the custom hash for ntdll.dll.
  2. bcrypt.dll is loaded with LoadLibraryW; kernelbase.dll is found by hash.
  3. Export tables are parsed to resolve native, fiber, resource, and BCrypt functions by hash.
  4. GetSysCallByWalking derives system service numbers and usable syscall instruction addresses for four native calls.
  5. Gdgt = FindROPGadget() scans executable ntdll sections for 41 FF D4, the x64 encoding of call r12.

Hashing and PE Walking

WEIRDHASHA combines a DJB2-like repeated multiplication phase, a DWORD derived from the input string, and the string length. Two fixed iteration counts define separate namespaces: 28 iterations for module paths and 27 for exported function names. The resulting numeric constants are embedded throughout the code.

GetLoadedDllHandleH walks PEB.Ldr.InLoadOrderModuleList, converts each full DLL path from wide characters to single-byte characters, hashes it, and returns the matching image base. GetFunctionAddressH parses the PE export directory and hashes each exported name. Name-based variants exist for development or non-hashed lookup.

GetSysCallByWalking starts at the requested Nt* export and advances in 0x20-byte increments until it finds a stub considered unhooked. It derives the target service number relative to that neighbor and records the neighbor's syscall instruction as a decoy dispatch location. syscalls.asm loads the derived service number into EAX, moves the first argument into R10, and jumps to the selected syscall instruction.

Return-Address Spoofing

RetSpoofCall is the common call gateway for normal APIs, native APIs, C runtime routines, and the indirect syscall wrappers. Its logical calling convention is:

RetSpoofCall(targetFunction, argumentCount, callR12Gadget, firstArgument, ...);

The assembly routine shifts arguments into the Windows x64 ABI locations, places the chosen call r12 gadget where the target will return, and uses an internal Fixup label to restore nonvolatile registers and the original stack frame. This creates a synthetic return chain for calls made through the gateway.

Main Runtime Flow

The loader performs preparation before exposing plaintext payload bytes as executable memory.

1. Restore ntdll

FlushNTDLL obtains a clean in-memory image rather than reading the DLL from disk:

  1. GetImageSizeFromBase validates the local DOS and NT headers and reads SizeOfImage.
  2. NtCreateUserSuspendedProcess constructs native process parameters for \??\C:\Windows\System32\audiodg.exe and creates it suspended through SysNtCreateUserProcess.
  3. ReadBufferFromProcess reads an image-sized range beginning at the local ntdll base address from the suspended process.
  4. The temporary process is terminated.
  5. FlushNTDLL locates .text in the local image, temporarily applies PAGE_EXECUTE_WRITECOPY, copies the corresponding bytes from the clean buffer, and restores the old protection.

This path depends on ntprocessapi.h and the process-related layouts in structs.h, especially RTL_USER_PROCESS_PARAMETERS, PS_CREATE_INFO, PS_ATTRIBUTE, and PS_ATTRIBUTE_LIST.

2. Patch ETW Entry Points

PatchETW resolves NtTraceEvent and NtTraceControl by hash, selects byte offset +3 in each routine, makes one byte writable, and writes 0xC3 (ret). ValidateMemory compares the patched byte with the source byte before protections are restored. This is an explicit process-local telemetry suppression step and is tightly coupled to the expected machine-code layout of those exports.

3. Retrieve and Decrypt the Payload

GetFromRc uses dynamically resolved resource APIs to find, load, lock, and size IDR_RCDATA1. main copies the locked resource bytes into a heap buffer before passing them to AESDecrypt.

AESDecrypt validates inputs, populates an AES context, and delegates to InternalAESDecrypt. The internal routine:

  1. Opens the BCrypt AES provider.
  2. Queries key-object and block sizes and requires a 16-byte AES block.
  3. Configures CBC chaining.
  4. Generates a symmetric key from the embedded 32-byte key.
  5. Calls BCryptDecrypt once to size the output and again to produce plaintext with block-padding removal.
  6. Destroys the key, closes the provider, frees the key object, and returns the plaintext allocation through the context.
flowchart LR Binary[Ghost.exe resource] Locked[Locked ciphertext view] CipherHeap[Ciphertext heap copy] Context[AES context] Provider[BCrypt AES CBC provider] Plain[Plaintext payload] Binary --> Locked --> CipherHeap --> Context Key[Embedded 32 byte key] --> Context IV[Embedded 16 byte IV] --> Context Context --> Provider --> Plain

4. Obscure the Payload in Memory

allocate_large_page creates a LARGE_PAGE_INFORMATION context and requests a region sized approximately PlainBufferSize * 2048, rounded to a page boundary. It fills the entire region with bytes from SystemFunction036 (RtlGenRandom), chooses a random offset, and sets lpData to that location. place_data_rand copies the plaintext payload to lpData.

After placement, main changes protection on the entire allocation from read/write to execute/read. The design trades a very large executable allocation for a low payload-to-noise ratio within that allocation.

LARGE_PAGE_INFORMATION carries the allocation contract:

Field Meaning
dwOffset Random byte offset selected within the allocation.
uSize Total aligned allocation size passed to native memory APIs.
lpPage Base address of the allocation.
lpData Intended payload entry point at lpPage + dwOffset.

5. Execute and Sleep Through Fibers

HookFunction overwrites the beginning of kernel32!Sleep with a 13-byte absolute trampoline: load the destination into R10, then jump to R10. The destination is FiberSwitcher.

The current thread is converted to InitialFiber, and a second fiber is created with pLPI->lpData as its start routine. The main loop switches to this payload fiber. When the payload calls Sleep(milliseconds), the hook routes execution to FiberSwitcher, which stores the delay in dwSleepTime and switches back to InitialFiber. The loader then calls DelayExecution, which creates an event and waits through NtWaitForSingleObject using a negative relative timeout. When the wait ends, the main loop switches back to the payload fiber.

sequenceDiagram participant Main as Initial fiber participant Payload as Payload fiber participant Sleep as Hooked Sleep participant Switcher as FiberSwitcher participant NativeWait as DelayExecution Main->>Payload: SwitchToFiber Payload->>Sleep: Sleep milliseconds Sleep->>Switcher: Absolute trampoline Switcher->>Switcher: Save dwSleepTime Switcher->>Main: SwitchToFiber InitialFiber Main->>NativeWait: Wait for dwSleepTime NativeWait-->>Main: Timeout completed Main->>Payload: SwitchToFiber

This mechanism assumes the embedded payload sleeps through the hooked Sleep entry point. Payloads that use SleepEx, waitable timers, thread-pool waits, or another sleep primitive will not enter this control path without adaptation.

The design relies on process-wide globals rather than explicit dependency injection:

Important buffer ownership contracts are implicit:

  • GetFromRc returns a borrowed pointer into the executable resource; the caller does not free it.
  • AESDecrypt returns a heap allocation created with malloc; the caller owns it.
  • allocate_large_page returns both a heap-allocated context and an NT virtual-memory allocation; the caller owns both.
  • ReadBufferFromProcess returns a heap allocation through its output parameter; FlushNTDLL owns it.

Failure Handling and Observability

The code primarily reports failures to std::cout/fprintf and either returns early or relies on macros from defs.h. There is no structured error object, centralized cleanup, retry policy, or rollback of partially completed preparation. _DEBUG_PRINT is defined in defs.h, so debug messages are enabled unless the definition is removed before compilation.

The preparation steps are not transactional. For example, one ETW function may be patched even if patching the other fails, and a failed stage can leave handles, memory, or modified protections behind. The main loop has no shutdown condition and is expected to live for the lifetime of the payload.

Platform and Design Assumptions

  • The build environment uses the exact absolute tool paths declared in build.py.
  • The target and payload are x64; both assembly implementations and the use of __readgsqword(96) are architecture-specific.
  • Internal Windows structures and export layouts match the declarations in structs.h and types.h.
  • Hashed DLL paths and exports produce the constants embedded in the source.
  • ntdll syscall stubs have the expected size, ordering, prologue, and syscall offset.
  • The suspended process maps ntdll compatibly with the local process for the chosen read base.
  • NtTraceEvent and NtTraceControl tolerate the hard-coded patch location.
  • The payload can execute as an LPFIBER_START_ROUTINE and yields through the exact hooked sleep API.
  • The payload fits entirely between the selected random offset and the end of the large allocation.

Maintenance Risks and Known Fragility

These constraints are important when changing or testing the module:

  • allocate_large_page chooses an offset from the whole allocation without reserving cbBuffer bytes at the end. A high offset can make place_data_rand write beyond the region.
  • FindROPGadget selects with an inclusive upper bound, so it can index one element past the discovered gadget list; it also has no safe zero-gadget path.
  • Buffers created with malloc are released with delete[] in FlushNTDLL and main, which is undefined behavior. They should be paired with free.
  • IsHooked uses a conjunction across byte mismatches. A stub is classified as hooked only when all checked bytes differ, allowing partially modified prologues to pass as clean.
  • Export parsing does not handle forwarded exports, malformed images, or absent export directories robustly.
  • PEB module walks have no list-termination or not-found condition and can loop indefinitely.
  • NtCreateUserSuspendedProcess does not stop after a failed RtlCreateProcessParametersEx call and does not release the returned process parameters.
  • Process/thread/event handles, the fiber, the large memory region, and its context are not fully cleaned up.
  • HookFunction overwrites 13 bytes without disassembling instruction boundaries or preserving a callable trampoline to the original function.
  • ETW patch offsets and syscall-neighbor arithmetic are Windows-build-sensitive implementation assumptions.
  • build.py treats any stderr output as a build failure instead of checking the subprocess return code, and its regex replacement assumes exact source declarations.
  • WIN_MAIN is declared in build.py but unused, while the source defines main; GUI versus console subsystem behavior depends on linker defaults and toolchain configuration.
  • Global definitions in headers are safe only while the program remains a single translation unit. Including them from additional .cpp files would create one-definition-rule/linkage problems.

Extension Points

The architecture permits several targeted substitutions, but each crosses a clearly defined boundary:

  • Payload packaging: Replace build.py encryption/resource generation together with rsrc.h and AES.h; build-time and runtime formats must remain synchronized.
  • API resolution: Change hash.h or resolvers.h, then regenerate every embedded module/function hash consumed by functions.h and other headers.
  • Native invocation: Replace RetSpoofCall or the indirect syscall wrappers while preserving the Windows x64 ABI and all call sites' argument-count convention.
  • Sleep integration: Replace the hooked API and FiberSwitcher contract for payloads that do not call Sleep.
  • Memory strategy: Replace LARGE_PAGE_INFORMATION, allocate_large_page, and place_data_rand while preserving lpData as a valid fiber entry address and an executable protection transition.
  • Clean-image source: Replace the suspended-process strategy in unhook.h while preserving an image buffer whose section RVAs correspond to local ntdll.

End-to-End Summary

Ghost's central design is a staged transformation and execution pipeline. At build time, raw shellcode becomes AES-CBC ciphertext embedded in the executable, with the corresponding key and IV written into the C++ source. At runtime, the loader establishes its resolution/spoofing substrate, restores selected native code, suppresses two ETW paths, decrypts the resource, hides the plaintext among random bytes, and starts it as a fiber. A permanent Sleep hook transfers control back to the loader so the actual delay occurs on the initial fiber before payload execution resumes.

The major architectural coupling is the global RetSpoofCall path: resolution, decryption, memory operations, resource access, process creation, hooking, and fiber scheduling all depend on the same resolved function table and Gdgt gadget. The second major coupling is the payload sleep contract, which determines whether the fiber scheduler ever regains control after execution begins.
